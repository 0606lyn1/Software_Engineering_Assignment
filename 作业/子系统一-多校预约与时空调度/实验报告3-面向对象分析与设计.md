# 实验报告三：面向对象分析与设计实践

**实验名称：** 实验三 面向对象分析与设计实践

**子系统：** 子系统一——多校体育场地预约与时空调度子系统

**对应代码：** `ReservationController.java`、`ReservationServiceImpl.java`、`Reservation.vue`

---

## 报告说明

本报告运用面向对象分析方法，识别子系统一的参与者与用例，绘制用例图并撰写用例规格说明。用例模型严格对照当前已实现功能，剔除教学占场、时段锁定、附近推荐等尚未编码的用例。

## 一. 实验目的

1. 掌握用例驱动分析方法，识别系统参与者与用例。
2. 绘制规范的 UML 用例图，表达参与者与用例的关联关系。
3. 为核心用例撰写完整规格说明（前置/后置条件、基本流、异常流）。
4. 使用例规格可直接映射到 `ReservationController` 接口与前端页面。

## 二. 实验内容

识别参与者，绘制用例图，针对"创建预约""查看我的预约""删除预约""管理员查看全量预约"四个核心用例撰写规格说明。

### 3. 用例规格说明

#### UC-1 创建场地预约

| 属性 | 内容 |
| --- | --- |
| **用例编号** | UC-1 |
| **用例名称** | 创建场地预约 |
| **参与者** | 学生、教师、管理员 |
| **简述** | 用户选择场馆与起止时间，提交预约请求，系统校验后创建 BOOKED 状态记录 |
| **优先级** | 高 |

**前置条件：**
1. 用户已通过 JWT 登录，角色为 STUDENT/TEACHER/ADMIN/USER。
2. 用户已选择目标场馆（venueId）和起止时间。

**后置条件（成功）：**
1. `t_reservation` 新增一条记录，status = `BOOKED`。
2. 前端跳转至 `/my-reservations` 并显示成功提示。

**后置条件（失败）：**
1. 无新记录写入，返回 `BusinessException` 错误信息。

**基本事件流：**

| 步骤 | 动作 | 实现 |
| --- | --- | --- |
| 1 | 用户打开 `/reservation` 页面 | `Reservation.vue` onMounted |
| 2 | 系统加载场馆列表 | `api.getVenues()` → GET /api/venues |
| 3 | 用户选择场馆、起止时间 | DatePicker 或 `setQuickTime()` |
| 4 | 前端校验 start < end | `onSubmit()` L61-64 |
| 5 | 用户点击提交 | `api.createReservation()` |
| 6 | 后端校验时间合法性 | `createReservation()` L27-29 |
| 7 | 后端调用子系统二校验可约性 | `getAvailability(venueId)` |
| 8 | 后端检测同用户重叠预约 | `lambdaQuery()` L36-44 |
| 9 | 后端写入预约记录 status=BOOKED | `save(reservation)` |
| 10 | 返回成功，前端跳转我的预约 | `router.push('/my-reservations')` |

**异常事件流：**

| 异常 | 条件 | 系统响应 |
| --- | --- | --- |
| E1 | start >= end | "预约时间不合法，开始时间必须早于结束时间" |
| E2 | 场地运维阻断 | "场地暂不可预约：{reason}" |
| E3 | 同用户时段重叠 | "预约冲突：该用户在该场地已有重叠预约" |
| E4 | 未选择场馆/时间 | 前端 "请先选择场馆/完整时间段" |

#### UC-2 查看我的预约

| 属性 | 内容 |
| --- | --- |
| **用例编号** | UC-2 |
| **用例名称** | 查看我的预约 |
| **参与者** | 学生、教师、管理员 |
| **简述** | 用户查看自己创建的所有预约记录 |

**前置条件：** 用户已登录。

**基本事件流：**
1. 用户进入 `/my-reservations`。
2. 前端调用 `GET /api/reservations`。
3. `ReservationController.list()` 根据 JWT 用户名查询 `userId`，返回该用户全部预约。
4. 前端以表格展示场馆、起止时间、状态。

**异常事件流：** 用户不存在 → "当前用户不存在"。

---

#### UC-3 删除预约

| 属性 | 内容 |
| --- | --- |
| **用例编号** | UC-3 |
| **用例名称** | 删除预约 |
| **参与者** | 学生/教师（本人）、管理员/运维（任意） |
| **简述** | 用户删除指定预约记录（物理删除） |

**前置条件：** 预约记录存在。

**基本事件流：**
1. 用户在"我的预约"页点击删除。
2. 前端调用 `DELETE /api/reservations/{id}`。
3. 后端校验：非 ADMIN/STAFF 时须为本人预约。
4. `reservationService.removeById(id)` 物理删除。
5. 返回 "删除成功"。

**异常事件流：**
- 预约不存在 → "预约不存在"
- 无权删除 → "无权删除该预约"

#### UC-5 管理员查看全量预约

| 属性 | 内容 |
| --- | --- |
| **用例编号** | UC-5 |
| **用例名称** | 管理员查看全量预约 |
| **参与者** | 管理员、运维人员 |
| **简述** | 以全量模式查看系统所有预约记录 |

**前置条件：** 角色为 ADMIN 或 STAFF。

**基本事件流：**
1. 调用 `GET /api/reservations?all=true`。
2. `ReservationController` 判断 `isAdminOrStaff()` 为 true。
3. 返回 `reservationService.list()` 全量数据。

## 四. 实验总结

### 实验中遇到的问题

原用例图包含 14 个用例，其中教学占场、时段锁定、超时自动取消等未在代码中实现，导致用例与实现脱节。

### 解决方法

按"代码中存在对应 Controller 方法或前端页面"的原则筛选用例，保留 5 个已实现用例并补充精确到类名/方法名的事件流。

### 思考与收获

用例规格说明中引用 `createReservation()`、`getAvailability()`、`removeById()` 等具体方法，使 OO 分析结果可直接用于测试用例编写和接口验收，体现了用例驱动分析与实现的一致性。
