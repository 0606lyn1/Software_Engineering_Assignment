# 实验报告三：面向对象分析与设计实践

**实验名称：** 实验三 面向对象分析与设计实践

**子系统：** 子系统一——多校体育场地预约与时空调度子系统

---

## 一、实验目的

本实验旨在运用面向对象分析与设计方法，对多校体育场地预约与时空调度子系统进行用例驱动的分析与建模。主要目标如下：

1. 掌握用例驱动分析的方法，识别系统参与者与用例。
2. 掌握用例图的绘制规范，正确表达参与者与用例之间的关联关系以及用例间的包含（include）与扩展（extend）关系。
3. 为每个核心用例撰写完整的用例规格说明，包括前置条件、后置条件、基本流程与异常流程。
4. 培养运用用例分析方法完整描述系统功能需求的能力。

---

## 二、参与者识别

对子系统一的参与者进行分析，识别出以下系统参与者：

| 参与者 | 类型 | 说明 |
|--------|------|------|
| **学生 (Student)** | 主要参与者 | 系统的最大用户群体，使用系统进行课外体育场地的查询、预约、取消与评价 |
| **教师 (Teacher)** | 主要参与者 | 使用系统进行课程教学场地的周期占场管理与课程统计查看 |
| **管理员 (Admin)** | 主要参与者 | 全局管理人员，负责场馆管理、时段锁定、用户管理、租户配置 |
| **时间 (Time)** | 外部参与者 | 系统定时器/调度器，触发超时自动取消、预约到期自动完成等定时任务 |
| **子系统二（器材管理）** | 外部系统 | 与本子系统通过API交互，查询器材状态以辅助场馆预约决策 |
| **子系统三（赛事组织）** | 外部系统 | 与本子系统通过API交互，同步赛事日程以协调场馆使用 |

### 3.3 用例关系分析

#### include（包含）关系

当基用例的执行必须依赖被包含用例的结果时，使用`<<include>>`关系，表示基用例在流程中一定会调用被包含用例。

| 基用例 | 包含用例 | 说明 |
|--------|----------|------|
| 提交课外预约 | 查询时段可用性 | 预约提交前必须先查询目标场馆指定时段的可用性状态，时段网格中的绿色（可用）/灰色（已占用）标记即由该用例支撑 |
| 锁定时段/闭馆 | 查看全系统预约 | 管理员执行锁定操作前需查看全系统预约以评估影响范围，确认受影响预约后再执行锁定操作 |

#### extend（扩展）关系

当基用例在特定条件分支下可选择性地触发扩展用例时，使用`<<extend>>`关系。

| 基用例 | 扩展用例 | 扩展条件 |
|--------|----------|----------|
| 提交课外预约 | 查看附近推荐 | 用户通过推荐入口进入预约流程时，先执行推荐逻辑再进入常规预约步骤 |
| 用户与权限管理 | 租户配置 | 管理员进行多校多租户场景下的权限隔离配置时触发该扩展 |

#### 泛化（Generalization）关系

在本系统的数据模型层面，教师和学生均为系统用户（User）的泛化特化关系，具备用户的基本属性（用户名、密码、角色标识等）并各自具有特化的业务行为。在参与者层面，教师、学生和管理员作为三类独立的参与者平级存在；在类设计层面，可设计User基类，由其派生出Student和Teacher子类，共享公共属性与方法。

## 四、用例规格说明

### UC-1 学生课外预约场地

| 属性 | 内容 |
|------|------|
| **用例编号** | UC-1 |
| **用例名称** | 学生课外预约场地 |
| **参与者** | 学生(Student) |
| **简述** | 学生登录系统后，浏览场馆清单，选择目标场馆与可用时段，提交预约申请，系统校验后完成预约。 |
| **优先级** | 高 |
| **关系** | include: 查询时段可用性; extend: 查看附近推荐 |

**前置条件：**
1. 学生已通过JWT认证登录系统。
2. 学生处于校园网络环境中（或已通过VPN接入）。
3. 学生已选择目标场馆及至少一个连续的可用时段。
4. 预约时段处于系统开放时间窗口（06:00-22:00）内。

**后置条件（成功）：**
1. 预约记录以PENDING状态写入数据库（t_reservation表）。
2. 所选时段在公众预约视图中标记为"已占用"。
3. 学生收到预约提交成功的确认通知。
4. 预约行为记录写入审计日志。

**后置条件（失败）：**
1. 系统状态不变，预约未创建。
2. 学生收到明确的错误提示及建议操作。

**基本流程：**

| 步骤 | 描述 |
|------|------|
| 1 | 学生点击首页"立即预约"按钮或导航至预约页面(Reservation.vue)。 |
| 2 | 系统展示场馆选择下拉框（支持搜索），学生输入关键词筛选并选择目标场馆。 |
| 3 | 系统加载所选场馆的基本信息卡（名称、类型、价格、描述）及可用性概况。 |
| 4 | 学生通过日期选择器选择预约日期。 |
| 5 | 系统渲染16格时段网格（06:00-22:00），绿色=可用，灰色=已占用（教学占场或已有预约）。 |
| 6 | 学生点击一个绿色时段格作为起始时段，系统自动高亮连续时段为蓝色（选定状态），并展开结束时段选择。 |
| 7 | 学生在预约摘要栏确认场馆名称、日期、时段和总价，点击"确认预约"按钮。 |
| 8 | 前端向POST /api/reservations提交ReservationCreateRequest（venueId, startTime, endTime）。 |
| 9 | ReservationController接收请求，委托ReservationService.createReservation()处理。 |
| 10 | 服务端执行时间有效性校验（start<end且end不在过去）。 |
| 11 | 服务端通过VenueOpsService.evaluateAvailability()检测教学占场与管理员锁定。 |
| 12 | 服务端查询同场馆同时段非CANCELLED预约记录进行冲突检测。 |
| 13 | 服务端检测用户自身并发限制（同时段不可有其他预约）。 |
| 14 | 在MySQL事务中执行INSERT，采用乐观锁版本号机制。 |
| 15 | 预约成功，返回ApiResponse.success（含预约详情）。 |
| 16 | 系统异步触发NotificationService发送预约确认通知。 |
| 17 | 前端跳转至预约成功提示页面，显示预约编号和详细信息。 |

**异常流程：**

| 步骤 | 描述 |
|------|------|
| E1 | **时段被抢先预约**：在第12步检测到冲突预约，系统返回"该时段已被他人预约，请重新选择时段"错误提示。前端刷新时段网格，学生重新选择。 |
| E2 | **权限不足**：在第8步或第10步中，若学生角色无预约权限或被禁用，返回HTTP 403"权限不足，请联系管理员"。 |
| E3 | **网络异常**：在第8步中，若网络超时或服务不可用，前端捕获Axios请求异常，展示"网络连接失败，请检查网络后重试"提示并启用重试按钮。 |
| E4 | **场馆维护中**：在第11步中，evaluateAvailability返回LOCKED状态，返回"该场馆当前维护中/已闭馆，暂不接受预约"提示，建议选择其他场馆。 |
| E5 | **并发乐观锁冲突**：在第14步中，若乐观锁版本号不匹配（另一用户同时提交了同一时段），事务回滚，返回"时段已被抢先预约，请重新选择"。 |

### UC-2 教师维护课程占场

| 属性 | 内容 |
|------|------|
| **用例编号** | UC-2 |
| **用例名称** | 教师维护课程教学占场 |
| **参与者** | 教师(Teacher) |
| **简述** | 教师为所授课程创建周期性教学占场规则，指定场地、学期、周次与时段，系统自动将规则中时段从学生公开预约池中排除。 |
| **优先级** | 高 |
| **关系** | — |

**前置条件：**
1. 教师已通过JWT认证登录系统。
2. 教师具有TEACHER角色权限。
3. 教师已关联至少一门课程。

**后置条件（成功）：**
1. 教学占场规则写入t_teaching_occupy（或等效存储）表。
2. 规则中的时段在预约网格中自动标记为灰色（不可预约）。
3. 若规则生效期间已有学生预约冲突，系统自动取消冲突预约并推送通知。

**基本流程：**

| 步骤 | 描述 |
|------|------|
| 1 | 教师登录系统后进入"教学占场管理"页面。 |
| 2 | 教师选择关联课程，点击"新建占场规则"。 |
| 3 | 系统展示规则配置表单：选择场馆、设置学期、设置周次范围或每周循环模式（如每周一/周三）、设置时段（起始时间+结束时间）。 |
| 4 | 系统支持添加例外日期列表（如法定节假日、考试周），例外日期时段自动释放。 |
| 5 | 教师提交规则，系统校验规则参数合法性。 |
| 6 | 系统检测规则覆盖时段内是否存在学生预约冲突，如有则提示教师确认是否强制覆盖并通知学生。 |
| 7 | 教师确认后，规则写入数据库，冲突预约自动取消。 |
| 8 | 系统返回占场规则创建成功，并在教师甘特图视图中展示。 |

**异常流程：**

| 步骤 | 描述 |
|------|------|
| E1 | **时段与已有占场冲突**：在第6步检测到同一场馆同时段已有教学占场，返回"该时段已被其他课程占用"提示。 |
| E2 | **场馆不存在或不可用**：在第3步中选择的场馆已被关闭，返回"所选场馆不可用"提示。 |
| E3 | **规则参数非法**：在第5步中，起始时间晚于或等于结束时间，返回"时间设置不合法"提示。 |
| E4 | **权限不足**：非教师角色访问该功能，返回HTTP 403。 |

### UC-3 管理员临时闭馆

| 属性 | 内容 |
|------|------|
| **用例编号** | UC-3 |
| **用例名称** | 管理员锁定时段/临时闭馆 |
| **参与者** | 管理员(Admin) |
| **简述** | 管理员因维修、赛事或节假日需要对某个场馆的指定时段进行一键锁定，锁定后该时段不可被预约，已存在的预约自动取消并通知对应用户。 |
| **优先级** | 高 |
| **关系** | include: 查看全系统预约 |

**前置条件：**
1. 管理员已通过JWT认证登录系统。
2. 管理员具有ADMIN角色权限。
3. 目标场馆存在于系统中。

**后置条件（成功）：**
1. 锁定记录写入t_lock_record（或等效存储）表。
2. 锁定覆盖时段内所有已存在的学生预约自动标记为CANCELLED，并释放时段。
3. 收到通知推送的受影响学生会收到取消原因说明。
4. 锁定记录写入审计日志。

**基本流程：**

| 步骤 | 描述 |
|------|------|
| 1 | 管理员登录管理后台，进入"场馆管理"→"时段锁定"页面。 |
| 2 | 管理员通过场馆选择器选择目标场馆（支持按类型筛选）。 |
| 3 | 管理员通过日期选择器与时段选择器设定锁定的时间范围。 |
| 4 | 系统展示该时段内当前预约列表供管理员预览影响范围。 |
| 5 | 管理员填写锁定原因（维修/赛事/其他），点击"确认锁定"。 |
| 6 | 系统在数据库事务中：a) 插入锁定记录；b) 查询并批量取消冲突预约；c) 写入每一条取消的审计日志。 |
| 7 | 系统异步触发NotificationService，向所有受影响用户推送取消通知。 |
| 8 | 管理界面刷新，锁定时段在甘特图中以红色标记显示。 |

**异常流程：**

| 步骤 | 描述 |
|------|------|
| E1 | **时段选择无效**：在第3步中，结束时间早于起始时间，前端表单校验拦截，展示"结束时间不能早于开始时间"提示。 |
| E2 | **场馆已被锁定**：在第6步中，目标时段已存在锁定记录，返回"该时段已被锁定，不可重复操作"。 |
| E3 | **事务失败**：在第6步中，若批量取消操作部分失败，整个事务回滚，返回"操作失败，请重试"。 |
| E4 | **权限不足**：非管理员角色访问该功能，返回HTTP 403。 |

### UC-4 查看推荐并跳转预约

| 属性 | 内容 |
|------|------|
| **用例编号** | UC-4 |
| **用例名称** | 查看附近场馆推荐并跳转预约 |
| **参与者** | 学生(Student) |
| **简述** | 学生通过首页或推荐模块查看按距离排序的附近场馆推荐列表，点击任一推荐场馆查看其最近可用时段，并可直接跳转至预约页面。 |
| **优先级** | 中 |
| **关系** | include: 浏览场馆列表 |

**前置条件：**
1. 学生已通过JWT认证登录系统。
2. 若学生授权了地理位置权限，系统使用GPS/WiFi定位获取坐标。
3. 若学生未授权地理位置，系统使用学校默认校区坐标作为降级方案。

**后置条件（成功）：**
1. 推荐结果列表在前端渲染，每个推荐项包含场馆名称、距离、最近可用时段。
2. 学生点击推荐项后直接跳转至预约页面并预填充场馆信息。

**基本流程：**

| 步骤 | 描述 |
|------|------|
| 1 | 学生进入首页，系统自动发起推荐请求（或用户点击"附近场馆"入口）。 |
| 2 | 系统检测学生地理位置授权状态。 |
| 3a | [已授权] 系统通过浏览器Geolocation API获取当前位置经纬度。 |
| 3b | [未授权] 系统使用学生所属学校的默认校区坐标进行降级计算。 |
| 4 | 后端RecommendationService计算各场馆与学生的距离，按距离升序排序。 |
| 5 | 对于每个推荐场馆，系统查询其最近的一个可用时段（不含教学占场与锁定时段）。 |
| 6 | 系统返回推荐列表（场馆信息+距离+最近可用时段），前端以卡片列表渲染。 |
| 7 | 学生浏览推荐列表，点击感兴趣的场馆卡片。 |
| 8 | 前端路由跳转至Reservation.vue，并自动填充目标场馆（通过路由参数或Pinia状态传递）。 |
| 9 | 学生继续完成时段选择与预约提交（参见UC-1基本流程第5-17步）。 |

**异常流程：**

| 步骤 | 描述 |
|------|------|
| E1 | **地理位置获取失败**：在第3a步中，浏览器Geolocation API超时或返回错误，系统自动降级为3b（校区默认坐标），不静默复用缓存坐标。 |
| E2 | **推荐列表为空**：在第5步中，若所有场馆在近期均无可预约时段，返回"当前所有场馆暂无可用时段，请稍后再试"。 |
| E3 | **用户已开启opt-out**：若学生在隐私设置中关闭了个性化推荐开关，系统降级为随机排序或按热度排序的默认场馆列表。 |
| E4 | **场馆已被锁定/关闭**：在第5步查询可用时段时跳过维护中或已关闭的场馆。 |

## 五、实验总结

通过本次面向对象分析与设计实践，完成了多校体育场地预约与时空调度子系统的用例驱动分析工作。主要收获如下：

1. **参与者识别**：识别出学生、教师、管理员三种人类参与者，以及时间（定时器）与外部子系统（器材管理、赛事组织）三种非人类参与者，全面覆盖了系统的交互边界。

2. **用例建模**：绘制了包含14个核心用例的UML用例图，正确表达了参与者与用例间的关联关系，以及用例间的include关系（如"提交课外预约"include"查询时段可用性"）和extend关系（如"提交课外预约"extend"查看附近推荐"），并通过用例关系分析表详细描述了各用例间的包含、扩展与泛化关系。

3. **用例规格说明**：为UC-1（学生课外预约）、UC-2（教师维护课程占场）、UC-3（管理员临时闭馆）、UC-4（查看推荐并跳转预约）四个核心用例撰写了完整的规格说明，每个用例均包含前置条件、后置条件、7+步骤的基本流程和4+步骤的异常流程，并在每个用例表中新增了"关系"行以明确该用例与其他用例的连接。

4. **业务规则梳理**：通过用例规格说明明确了教学占场优先于学生预约、乐观锁并发控制、地理位置降级策略等关键业务规则，为后续的静态建模与动态建模提供了准确的需求依据。
