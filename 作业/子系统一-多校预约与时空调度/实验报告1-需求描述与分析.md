# 实验报告一：需求描述与分析实验

**实验名称：** 实验一 需求描述与分析实验

**子系统：** 子系统一——多校体育场地预约与时空调度子系统

**对应代码：** `Software_Engineering_Assignment/stadium`（后端）+ `Software_Engineering_Assignment/first`（前端）

---

## 报告说明

本报告基于当前已实现的智慧校园体育场地预约系统，对子系统一进行需求描述与分析。系统采用 Spring Boot 3 + MyBatis-Plus + Spring Security JWT 后端与 Vue 3 + Ant Design Vue 前端，数据库为 MySQL `tiyu`。本子系统与子系统二（场地运维）共用同一单体应用，通过 `VenueOpsService.getAvailability()` 在预约创建前校验场地可约性。

**实现范围说明：** 当前版本已实现场馆浏览、自由时段预约、我的预约、删除预约、管理员全量查看等核心流程；多校租户隔离、16 格时段网格、教学占场规则、附近推荐、消息提醒等能力在需求层面保留为扩展项，尚未编码落地。

## 一. 实验目的

1. 掌握软件需求分析的基本方法与流程，理解需求工程在软件开发中的关键作用。
2. 梳理系统的用户角色及其对应的业务场景，明确不同角色在系统中的行为模式。
3. 开展技术可行性、经济可行性与操作可行性分析，评估项目实施的现实条件。
4. 对需求进行系统分类（功能需求与非功能需求），并撰写规范的需求规格说明书。
5. 使需求描述与当前系统代码实现保持一致，为后续建模与验收提供依据。

## 二. 实验内容

确定实验主题，梳理用户角色与业务场景，开展三维度可行性分析，定义功能与非功能需求，撰写需求规格说明书。需求分析以 `ReservationController`、`ReservationServiceImpl`、`Reservation.vue`、`MyReservations.vue` 等已实现模块为对照基准。

### 3. 可行性分析

#### 3.1 技术可行性

| 技术层 | 选型 | 可行性说明 |
| --- | --- | --- |
| 后端框架 | Java 17 + Spring Boot 3.4.4 | 项目已编译运行，入口类 `TiyuBackendApplication` |
| ORM | MyBatis-Plus 3.5.7 | `ReservationMapper`、`ReservationServiceImpl` 已落地 |
| 安全 | Spring Security + JWT | `JwtAuthenticationFilter` + `@PreAuthorize` 控制接口权限 |
| 数据库 | MySQL 8.4 | `db.sql` 定义 `t_reservation` 等表，含种子数据 |
| 前端 | Vue 3 + Vite + Ant Design Vue + TypeScript | `Reservation.vue`、`MyReservations.vue` 已完成 |

**结论：** 技术栈成熟，核心预约流程已在本地验证通过，技术可行。

#### 3.2 经济可行性

采用全开源技术栈，无软件许可费用；单体部署模式运维成本低，经济上可行。

#### 3.3 操作可行性

预约流程为"选场馆 → 选起止时间 → 提交"，与主流预约应用一致；前端提供快捷时段按钮（`setQuickTime`），学习成本低，操作可行。

### 6. 需求规格说明书（摘要）

**引言：** 本文档定义子系统一的软件需求，覆盖场馆查询、在线预约、预约管理与运维可约性联动。

**总体描述：** 主要用户为学生（高频预约）、教师（同接口预约）、管理员（全量管理与删除）。系统通过 RESTful API 与 Vue SPA 交互，统一响应格式为 `ApiResponse<T>`（`code=0` 表示成功）。

**数据约束（来自 `db.sql`）：**
- `t_reservation`：id, user_id, venue_id, start_time, end_time, status
- 预约状态当前仅写入 `BOOKED`；删除采用物理删除而非状态变更
- 取消检测过滤条件使用 `CANCELED`（单 L），与前端展示 `CANCELLED` 拼写不一致，属已知差异

**接口约束：**
- 创建预约：`POST /api/reservations`，请求体 `{ venueId, startTime, endTime }`
- 查询预约：`GET /api/reservations` 或 `?all=true`（管理员）
- 删除预约：`DELETE /api/reservations/{id}`

## 四. 实验总结

### 实验中遇到的问题

1. 需求范围与实现进度不一致：课程设计要求的多校租户、教学占场等能力尚未编码，需在报告中区分"已实现"与"规划中"。
2. 子系统边界交叉：场地可约性由子系统二维护，子系统一在 `createReservation()` 中消费，需在需求中明确接口契约。

### 解决方法

1. 以代码为准重新梳理需求，为每项功能标注实现状态（✅/⏳）。
2. 将跨子系统依赖单独列为 FR-4，明确 `getAvailability()` 为预约前置条件。

### 思考与收获

通过对照 `ReservationServiceImpl.java` 和前端 `Reservation.vue` 重新审视需求，发现当前系统的核心价值是"场馆目录 + 自由时段预约 + 运维状态联动"，而非完整的多校调度平台。本次需求分析为后续结构化建模、用例设计和动态交互图提供了与代码一致的需求基线。
