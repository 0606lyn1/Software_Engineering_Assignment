# 实验报告二：结构化分析与设计实验

**实验名称：** 实验二 结构化分析与设计实验

**子系统：** 子系统一——多校体育场地预约与时空调度子系统

---

## 一、实验目的

本实验旨在通过结构化分析与设计方法，对多校体育场地预约与时空调度子系统进行系统化的功能分析与架构设计。主要目标如下：

1. 掌握数据流图（DFD）的绘制方法，自顶向下分层描述系统的数据流动与处理逻辑。
2. 掌握实体关系图（ER图）的设计方法，清晰定义系统中的数据实体及其关系。
3. 掌握状态迁移图（STD）的绘制，描述核心对象在系统中的状态变化及触发条件。
4. 开展系统的总体设计与详细设计，完成模块划分、技术架构选型与核心算法描述。
5. 为后续的面向对象分析与设计提供结构化的参考蓝图。

## 二、分层数据流图（DFD）

数据流图采用自顶向下的分层方法，从顶层概览系统整体数据流动，逐步细化至底层处理细节。

### 2.1 顶层DFD图

顶层DFD将整个体育场馆预约系统抽象为一个处理过程（P0），展示系统与外部实体之间的数据交互。

**外部实体（External Entities）：**
- **学生**：提交预约请求与时段查询请求，接收预约确认结果与推荐列表。
- **教师**：提交教学占场规则，接收占场确认与使用统计。
- **管理员**：发出管理指令与锁定请求，接收管理视图与审计日志。
- **子系统二（器材管理）**：查询器材状态，同步场馆-器材关联信息。
- **子系统三（赛事组织）**：同步赛事日程以协调场馆预订。
- **数据库**：系统持久化数据的最终存储地。

### 2.2 0层DFD图

0层DFD将顶层过程细化为三大核心处理模块：

**P1 预约处理**：接收学生与教师的预约请求，执行冲突检测、可用性校验与状态变更。学生提交课外预约、教师提交教学占场规则均流经此模块。处理结果写入预约表与占场规则表。

**P2 信息查询**：响应场馆浏览、时段查询、推荐计算与学生个人时间线展示请求。读取场馆表与预约表获取可用性数据，计算推荐结果。

**P3 系统管理**：处理管理员发起的场馆CRUD、时段锁定、租户配置与权限控制指令。读写用户表、场馆表与锁定记录表。

**0层DFD图示：**

![](./结构化分析-DFD0层图.svg)

### 2.3 1层DFD图（P1预约处理的细化）

1层DFD对P1"预约处理"进行进一步分解，展示预约处理的内部子流程：

**P1.1 请求校验** → **P1.2 冲突检测** → **P1.3 保存预约** → **P1.4 通知推送**

- **P1.1 请求校验**：验证start_time < end_time、end_time不在过去、venue_id有效、用户身份与权限校验。
- **P1.2 冲突检测**：查询教学占场规则表排除已占用时段；查询预约表中同场馆同时段非CANCELLED记录；查询锁定记录表排除锁定时段；检测用户自身并发预约限制。
- **P1.3 保存预约**：通过数据库事务INSERT预约记录，采用乐观锁（version字段）防止并发冲突。若INSERT受乐观锁冲突影响则回滚。
- **P1.4 通知推送**：预约成功后触发站内消息创建，记录审计日志，推送浏览器通知。

数据流：
- 学生/教师 → P1.1(预约请求数据) → P1.2 → P1.3 → D3(预约表写入) → P1.4 → 学生/教师(确认通知)
- P1.2 ← D3(已有预约查询), D4(占场规则查询), D5(锁定记录查询)

## 三、ER实体关系图

本子系统涉及以下核心实体及其关系：

### 3.1 实体识别

| 实体 | 说明 | 核心属性 |
|------|------|----------|
| **User** | 系统用户 | id(PK), username, password(BCrypt), email, role, tenant_id |
| **Venue** | 体育场馆 | id(PK), name, type_id(FK), price, description, tenant_id |
| **VenueType** | 场馆类型 | id(PK), name(篮球场/羽毛球场/网球场等) |
| **Reservation** | 预约单 | id(PK), user_id(FK), venue_id(FK), start_time, end_time, status |

| **LockRecord** | 场馆锁定记录 | id(PK), venue_id(FK), start_time, end_time, reason |
| **Comment** | 用户评价 | id(PK), user_id(FK), venue_id(FK), rating, content |
| **VenueOps** | 场馆运维信息 | id(PK), venue_id(FK), status, last_check |

### 3.2 实体关系

- User **1 : N** Reservation（一个用户可发起多个预约）
- Venue **1 : N** Reservation（一个场馆可被多次预约）
- Venue **1 : N** TeachingOccupancy（一个场馆可有多个教学占场规则）
- Venue **1 : N** LockRecord（一个场馆可有多次锁定记录）
- Venue **1 : N** Comment（一个场馆可有多条评价）
- Venue **1 : 1** VenueOps（一个场馆对应一条运维信息）
- VenueType **1 : N** Venue（一种类型可有多个场馆）

## 四、状态迁移图

### 4.1 预约单（Reservation）状态机

预约单在系统中的生命周期包含以下状态：

| 状态 | 说明 | 触发条件 |
|------|------|----------|
| PENDING | 待确认 | 用户提交预约后进入，等待系统确认或管理员审核 |
| CONFIRMED | 已确认 | 系统校验通过后自动确认，或管理员手动确认 |
| COMPLETED | 已完成 | 到达预约结束时间后系统自动标记 |
| CANCELLED | 已取消 | 用户主动取消、管理员强制取消、或因场馆锁定连带取消 |

**迁移路径：**
- PENDING → CONFIRMED：系统校验通过/管理员审核通过
- PENDING → CANCELLED：用户取消 / 超时自动取消
- CONFIRMED → COMPLETED：到达end_time，系统自动完成
- CONFIRMED → CANCELLED：管理员强制取消 / 场馆锁定触发连带取消

### 4.2 场馆（Venue）状态机

| 状态 | 说明 | 触发条件 |
|------|------|----------|
| AVAILABLE | 可预约 | 场馆正常开放，可被学生预约 |
| MAINTENANCE | 维护中 | 管理员锁定时段进行维修/赛事/闭馆 |
| CLOSED | 已关闭 | 永久关闭，不再接受任何预约 |

**迁移路径：**
- AVAILABLE → MAINTENANCE：管理员启动临时锁定
- MAINTENANCE → AVAILABLE：维护完成，管理员解锁
- MAINTENANCE → CLOSED：永久关闭决策
- AVAILABLE → CLOSED：直接关闭（罕见，如拆除）

## 五、系统总体设计

### 5.1 技术架构分层

系统采用经典的四层架构模型，各层职责清晰、低耦合高内聚：

| 层次 | 技术组件 | 职责 |
|------|----------|------|
| **表示层** | Vue 3 + Ant Design Vue + Axios | 用户界面渲染、交互处理、API请求封装、路由管理(Pinia)、响应式移动端适配 |
| **业务逻辑层** | Spring Boot Controller + Service | RESTful API暴露、业务规则校验、预约冲突检测、推荐算法计算、事务管理 |
| **数据访问层** | MyBatis-Plus Mapper | 数据库访问、Lambda条件查询、分页查询、乐观锁支持 |
| **数据层** | MySQL 8.4 | 数据持久化存储、事务支持、索引优化、多租户数据隔离 |

### 5.2 功能模块划分

| 模块 | 包含组件 | 功能描述 |
|------|----------|----------|
| **预约管理模块** | ReservationController/Service/ServiceImpl/Mapper | 预约的创建(C)、查询(R)、取消(U)、状态变更(U)、删除(D) |
| **场馆查询模块** | VenueController/Service | 场馆列表查询、按类型筛选、详情展示、时段可用性网格计算 |
| **时间调度模块** | VenueOpsService | 可用性评估(evaluateAvailability)、冲突检测、教学占场与预约的调度协调、锁定管理 |
| **用户管理模块** | UserController/Service | 用户注册、登录(JWT)、角色管理、权限控制 |
| **推荐模块** | RecommendationService | 附近场馆排序、最近可用时段计算、用户行为数据收集与推荐算法 |

### 5.3 架构设计原则

- **单一职责**：每个模块/类只负责一项核心功能
- **依赖倒置**：Controller依赖Service接口而非实现类，通过Spring DI注入ServiceImpl
- **面向接口编程**：Service层定义接口，ServiceImpl提供具体实现
- **数据租户隔离**：所有数据操作按tenant_id自动过滤，中间件拦截注入租户上下文

### 5.4 模块接口定义

| 模块名 | 对外接口 | 输入 | 输出 | 调用方 |
|--------|---------|------|------|--------|
| **预约管理模块** | POST /api/reservations | ReservationCreateRequest(venueId, startTime, endTime) | ApiResponse\<Reservation\> | Vue前端(Reservation.vue) |
| **场馆查询模块** | GET /api/venues | venueType(optional), date(optional) | ApiResponse\<List\<Venue\>\> | Vue前端(VenueList.vue) |
| **时间调度模块** | evaluateAvailability() | venueId, startTime, endTime | AvailabilityResult(available, reason) | ReservationServiceImpl内部调用 |
| **用户管理模块** | POST /api/auth/login | LoginRequest(username, password) | ApiResponse\<JwtToken\> | Vue前端(Login.vue) |
| **用户管理模块** | POST /api/users | UserCreateRequest | ApiResponse\<User\> | 管理员后台(AdminManage.vue) |
| **推荐模块** | GET /api/recommendations/nearby | latitude, longitude(optional) | ApiResponse\<List\<Recommendation\>\> | Vue前端(Home.vue) |

## 六、详细设计——模块实现细节、接口定义与流程逻辑

### 6.1 预约创建接口定义

**REST端点：** `POST /api/reservations`

**请求体（ReservationCreateRequest）：**
| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| venueId | Long | 是 | 目标场馆ID |
| startTime | LocalDateTime | 是 | 预约开始时间（格式：yyyy-MM-dd HH:mm） |
| endTime | LocalDateTime | 是 | 预约结束时间（格式：yyyy-MM-dd HH:mm） |

**响应体（ApiResponse\<Reservation\>）：**
| 字段 | 类型 | 说明 |
|------|------|------|
| code | Integer | 状态码（200成功，4xx客户端错误，5xx服务端错误） |
| message | String | 提示信息 |
| data | Reservation | 预约详情（含id, venueId, userId, startTime, endTime, status, createdAt） |

**错误码约定：**
| HTTP状态码 | code | message |
|------------|------|---------|
| 400 | 40001 | 时段无效（开始时间晚于结束时间或结束时间为过去时间） |
| 409 | 40901 | 时段已被占用（其他用户已预约） |
| 409 | 40902 | 与自身已有预约冲突 |
| 409 | 40903 | 场馆已被管理员锁定/教学占场中 |
| 403 | 40301 | 权限不足 |

### 6.2 预约创建流程逻辑

```
function createReservation(request, userId):
    // Step 1: 时间有效性校验
    if request.startTime >= request.endTime:
        throw InvalidTimeException("开始时间必须早于结束时间")
    if request.endTime <= now():
        throw InvalidTimeException("结束时间不能是过去时间")

    // Step 2: 场馆可用性评估
    availability_result = VenueOpsService.evaluateAvailability(
        venueId=request.venueId,
        startTime=request.startTime,
        endTime=request.endTime
    )
    if not availability_result.available:
        throw VenueUnavailableException(availability_result.reason)
        // reason可能为: LOCKED(管理员锁定) / TEACHING_OCCUPIED(教学占场)

    // Step 3: 预约冲突检测
    conflicts = ReservationMapper.selectList(lambda:
        reservation.venueId == request.venueId
        AND reservation.status != CANCELLED
        AND (
            (reservation.startTime < request.endTime AND reservation.endTime > request.startTime)
        )
    )
    if conflicts is not empty:
        throw ConflictException("该时段已被预约")

    // Step 4: 用户自身并发限制检测
    user_conflicts = ReservationMapper.selectList(lambda:
        reservation.userId == userId
        AND reservation.status in [PENDING, CONFIRMED]
        AND ... // 同时段重叠检测
    )
    if user_conflicts is not empty:
        throw ConflictException("你已有同时段预约，不能重复预约")

    // Step 5: 保存预约（乐观锁）
    reservation = new Reservation(
        userId=userId,
        venueId=request.venueId,
        startTime=request.startTime,
        endTime=request.endTime,
        status="PENDING"
    )
    try:
        ReservationMapper.insert(reservation)
    except OptimisticLockException:
        throw ConcurrentConflictException("时段已被他人抢先预约，请重新选择")

    // Step 6: 发送通知
    NotificationService.notify(userId, "预约提交成功", reservation)

    return ApiResponse.success(reservation)
```

### 6.3 冲突检测接口定义

**方法签名：** `ConflictDetectionResult detectConflicts(ConflictDetectionRequest request)`

**请求参数（ConflictDetectionRequest）：**
| 字段 | 类型 | 说明 |
|------|------|------|
| venueId | Long | 目标场馆ID |
| startTime | LocalDateTime | 请求开始时间 |
| endTime | LocalDateTime | 请求结束时间 |
| userId | Long | 当前用户ID（用于检测自身并发限制） |

**返回结果（ConflictDetectionResult）：**
| 字段 | 类型 | 说明 |
|------|------|------|
| hasConflict | Boolean | 是否存在冲突 |
| conflictType | String | 冲突类型：OTHER_RESERVATION / SELF_CONFLICT / LOCKED / TEACHING_OCCUPIED |
| conflictDetail | String | 冲突详情说明 |
| conflictingRecords | List | 冲突的预约/锁定/占场记录列表 |

### 6.4 冲突检测流程逻辑

预约冲突检测基于时段重叠判定，核心逻辑如下：

**算法描述：**
1. 输入：场馆ID、请求开始时间(A)、请求结束时间(B)
2. 查询该场馆所有状态不为CANCELLED的预约记录
3. 设有预约记录的开始时间为S，结束时间为E
4. 满足 `S < B AND E > A` 的记录即为冲突预约
5. 同时检测教学占场规则：计算请求时段是否落入教学占场的时间窗口
6. 同时检测锁定记录：计算请求时段是否落入管理员锁定的时间窗口
7. 同时检测用户自身并发：同一用户在同一时段内是否有其他预约

**时间复杂度：** O(n) 依赖预约表查询结果数量，配合场馆+时间索引，查询效率高。

**并发控制：** 基于MyBatis-Plus的乐观锁机制（version字段）。在保存预约时检查版本号，若被其他事务先修改则回滚，确保同一时段同一场馆仅一个预约成功。

## 七、实验总结

通过本次结构化分析与设计实验，完成了多校体育场地预约与时空调度子系统的结构化建模与架构设计工作。主要收获如下：

1. **分层DFD建模**：绘制了顶层、0层与1层三级DFD图，清晰地描述了系统与外部实体（学生/教师/管理员/子系统二/子系统三）之间的数据交互，以及内部三大处理模块（预约处理/信息查询/系统管理）之间的数据流动关系。

2. **ER实体关系建模**：识别了8个核心实体（User/Venue/VenueType/Reservation/TeachingOccupancy/LockRecord/Comment/VenueOps），定义了实体间的1:N和1:1关系，明确了各实体的核心属性与主外键关联。

3. **状态迁移建模**：设计了预约单（PENDING→CONFIRMED→COMPLETED/CANCELLED）与场馆（AVAILABLE→MAINTENANCE→CLOSED）两套状态机，明确了状态转换的触发条件与约束规则。

4. **总体与详细设计**：完成了四层技术架构设计（表示层/业务逻辑层/数据访问层/数据层）与五大模块划分（预约管理/场馆查询/时间调度/用户管理/推荐），并通过伪代码详细描述了预约创建流程与冲突检测算法，同时补充了各模块的接口定义、API端点与接口契约，为开发实现提供了精确的输入输出规范。

本次实验为后续的面向对象建模（用例图、类图、交互图）提供了清晰的结构化蓝图。
