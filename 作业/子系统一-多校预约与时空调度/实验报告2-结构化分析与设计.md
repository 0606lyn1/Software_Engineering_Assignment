# 实验报告二：结构化分析与设计实验

**实验名称：** 实验二 结构化分析与设计实验

**子系统：** 子系统一——多校体育场地预约与时空调度子系统

---

## 一. 实验目的

本实验旨在通过结构化分析与设计方法，对多校体育场地预约与时空调度子系统进行系统化的功能分析与架构设计。主要目标如下：

1. 掌握数据流图（DFD）的绘制方法，自顶向下分层描述系统的数据流动与处理逻辑。
2. 掌握实体关系图（ER图）的设计方法，清晰定义系统中的数据实体及其关系。
3. 掌握状态迁移图（STD）的绘制，描述核心对象在系统中的状态变化及触发条件。
4. 开展系统的总体设计与详细设计，完成模块划分、技术架构选型与核心算法描述。
5. 为后续的面向对象分析与设计提供结构化的参考蓝图。

## 二. 实验内容

本实验运用结构化分析方法，对子系统一进行分层数据流建模、实体关系建模和状态迁移建模。在完成三层DFD图、ER图和状态迁移图的绘制后，开展系统的总体设计（四层架构、五大模块划分）和详细设计（预约创建流程、冲突检测算法、API接口契约），为后续面向对象分析与设计提供结构化参考蓝图。

## 三. 实验步骤和结果

### 1. 分层数据流图（DFD）

数据流图采用自顶向下的分层方法，从顶层概览系统整体数据流动，逐步细化至底层处理细节。

#### 1.1 顶层DFD图

顶层DFD将整个体育场馆预约系统抽象为一个处理过程（P0），展示系统与外部实体之间的数据交互。

**外部实体（External Entities）：**
- **学生**：提交预约请求与时段查询请求，接收预约确认结果与推荐列表。
- **教师**：提交教学占场规则，接收占场确认与使用统计。
- **管理员**：发出管理指令与锁定请求，接收管理视图与审计日志。
- **子系统二（器材管理）**：查询器材状态，同步场馆-器材关联信息。
- **子系统三（赛事组织）**：同步赛事日程以协调场馆预订。
- **数据库**：系统持久化数据的最终存储地。

![](./结构化分析-DFD顶层图.svg)

#### 1.2 0层DFD图

0层DFD将顶层过程细化为三大核心处理模块：

**P1 预约处理**：接收学生与教师的预约请求，执行冲突检测、可用性校验与状态变更。学生提交课外预约、教师提交教学占场规则均流经此模块。处理结果写入预约表与占场规则表。

**P2 信息查询**：响应场馆浏览、时段查询、推荐计算与学生个人时间线展示请求。读取场馆表与预约表获取可用性数据，计算推荐结果。

**P3 系统管理**：处理管理员发起的场馆CRUD、时段锁定、租户配置与权限控制指令。读写用户表、场馆表与锁定记录表。

**0层DFD图示：**

![](./结构化分析-DFD0层图.svg)

#### 1.3 1层DFD图（P1预约处理的细化）

1层DFD对P1"预约处理"进行进一步分解，展示预约处理的内部子流程：

**P1.1 请求校验** → **P1.2 冲突检测** → **P1.3 保存预约** → **P1.4 通知推送**

- **P1.1 请求校验**：验证start_time < end_time、end_time不在过去、venue_id有效、用户身份与权限校验。
- **P1.2 冲突检测**：查询教学占场规则表排除已占用时段；查询预约表中同场馆同时段非CANCELLED记录；查询锁定记录表排除锁定时段；检测用户自身并发预约限制。
- **P1.3 保存预约**：通过数据库事务INSERT预约记录，采用乐观锁（version字段）防止并发冲突。
- **P1.4 通知推送**：预约成功后触发站内消息创建，记录审计日志，推送浏览器通知。

### 3. 状态迁移图

#### 3.1 预约单（Reservation）状态机

预约单在系统中的生命周期包含以下状态：

| 状态 | 说明 | 触发条件 |
|------|------|----------|
| PENDING | 待确认 | 用户提交预约后进入 |
| CONFIRMED | 已确认 | 系统校验通过后自动确认，或管理员手动确认 |
| COMPLETED | 已完成 | 到达预约结束时间后系统自动标记 |
| CANCELLED | 已取消 | 用户主动取消、管理员强制取消、或因场馆锁定连带取消 |

**迁移路径：**
- PENDING → CONFIRMED：系统校验通过/管理员审核通过
- PENDING → CANCELLED：用户取消 / 超时自动取消
- CONFIRMED → COMPLETED：到达end_time，系统自动完成
- CONFIRMED → CANCELLED：管理员强制取消 / 场馆锁定触发连带取消

#### 3.2 场馆（Venue）状态机

| 状态 | 说明 | 触发条件 |
|------|------|----------|
| AVAILABLE | 可预约 | 场馆正常开放，可被学生预约 |
| MAINTENANCE | 维护中 | 管理员锁定时段进行维修/赛事/闭馆 |
| CLOSED | 已关闭 | 永久关闭，不再接受任何预约 |

### 4. 系统总体设计

系统采用经典的四层架构模型，各层职责清晰、低耦合高内聚：

### 5. 详细设计——模块实现细节、接口定义与流程逻辑

#### 5.1 预约创建接口定义

**REST端点：** `POST /api/reservations`

**请求体（ReservationCreateRequest）：**
| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| venueId | Long | 是 | 目标场馆ID |
| startTime | LocalDateTime | 是 | 预约开始时间（格式：yyyy-MM-dd HH:mm） |
| endTime | LocalDateTime | 是 | 预约结束时间（格式：yyyy-MM-dd HH:mm） |

**响应体（ApiResponse\<Reservation\>）：**
| 字段 | 类型 | 说明 |
|------|------|------|
| code | Integer | 状态码（200成功，4xx客户端错误，5xx服务端错误） |
| message | String | 提示信息 |
| data | Reservation | 预约详情（含id, venueId, userId, startTime, endTime, status, createdAt） |

#### 5.2 预约创建流程逻辑

```
function createReservation(request, userId):
    // Step 1: 时间有效性校验
    if request.startTime >= request.endTime:
        throw InvalidTimeException("开始时间必须早于结束时间")
    if request.endTime <= now():
        throw InvalidTimeException("结束时间不能是过去时间")

    // Step 2: 场馆可用性评估
    availability_result = VenueOpsService.evaluateAvailability(
        venueId=request.venueId,
        startTime=request.startTime,
        endTime=request.endTime
    )
    if not availability_result.available:
        throw VenueUnavailableException(availability_result.reason)

    // Step 3: 预约冲突检测
    conflicts = ReservationMapper.selectList(...)
    if conflicts is not empty:
        throw ConflictException("该时段已被预约")

    // Step 4: 用户自身并发限制检测
    user_conflicts = ReservationMapper.selectList(...)
    if user_conflicts is not empty:
        throw ConflictException("你已有同时段预约，不能重复预约")

    // Step 5: 保存预约（乐观锁）
    reservation = new Reservation(...)
    try:
        ReservationMapper.insert(reservation)
    except OptimisticLockException:
        throw ConcurrentConflictException("时段已被他人抢先预约，请重新选择")

    // Step 6: 发送通知
    NotificationService.notify(userId, "预约提交成功", reservation)

    return ApiResponse.success(reservation)
```

#### 5.3 冲突检测算法

预约冲突检测基于时段重叠判定，核心逻辑如下：

**算法描述：**
1. 输入：场馆ID、请求开始时间(A)、请求结束时间(B)
2. 查询该场馆所有状态不为CANCELLED的预约记录
3. 设有预约记录的开始时间为S，结束时间为E
4. 满足 `S < B AND E > A` 的记录即为冲突预约
5. 同时检测教学占场规则、锁定记录和用户自身并发限制

**并发控制：** 基于MyBatis-Plus的乐观锁机制（version字段），确保同一时段同一场馆仅一个预约成功。

## 四. 实验总结

### 实验中遇到的问题

1. **DFD分层粒度的把握**：在绘制DFD时，顶层图过于概括（仅一个处理过程P0），0层图又可能过于细化，分层粒度难以把握。1层图在细化P1预约处理时，需要考虑是否要将P2、P3也细化到同等深度，导致层次不统一。

2. **ER图中实体关系的识别**：TeachingOccupancy（教学占场规则）和LockRecord（锁定记录）与Venue的关系容易混淆，需要仔细区分两者的业务语义差异。

3. **乐观锁与冲突检测的时序问题**：在详细设计冲突检测算法时，冲突检测与乐观锁写入之间存在时间窗口，高并发下可能出现检测通过但写入失败的情况。

### 解决方法

1. **遵循结构化分层原则**：严格按照"顶层→0层→1层"的自顶向下细化策略，确保每层只比上一层增加一个细节层次。对于P2和P3，在本次实验中不继续细化，保持与P1同等的抽象级别，在需要时可在后续实验中展开。

2. **明确实体业务语义**：TeachingOccupancy是"周期性教学占场规则"，作用于整个学期；LockRecord是"临时性锁定事件"，作用于特定时段范围。通过在ER图中增加语义描述区分了二者的差异。

3. **优化并发控制策略**：将冲突检测与乐观锁写入放在同一个数据库事务中执行，在检测冲突时使用SELECT ... FOR UPDATE锁定相关行，确保在事务提交前不会有其他事务插入冲突记录，从根本上消除检测与写入之间的时间窗口。

### 思考与收获

通过本次结构化分析与设计实验，完成了多校体育场地预约与时空调度子系统的结构化建模与架构设计工作。主要收获如下：

1. **分层DFD建模**：绘制了顶层、0层与1层三级DFD图，清晰地描述了系统与外部实体之间的数据交互，以及内部三大处理模块之间的数据流动关系。

2. **ER实体关系建模**：识别了8个核心实体，定义了实体间的1:N和1:1关系，明确了各实体的核心属性与主外键关联。

3. **状态迁移建模**：设计了预约单与场馆两套状态机，明确了状态转换的触发条件与约束规则。

4. **总体与详细设计**：完成了四层技术架构设计与五大模块划分，通过伪代码详细描述了预约创建流程与冲突检测算法，为开发实现提供了精确的输入输出规范。
