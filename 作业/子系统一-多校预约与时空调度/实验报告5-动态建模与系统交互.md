# 实验报告五：动态建模与系统交互实践

**实验名称：** 实验五 动态建模与系统交互实践

**子系统：** 子系统一——多校体育场地预约与时空调度子系统

---

## 报告说明

本报告从运行行为角度描述子系统一在关键业务场景下的交互过程，是对前四次实验形成的需求模型、结构化模型、用例模型和静态模型的动态验证。静态模型说明系统由哪些对象组成，而动态模型进一步说明这些对象如何按时间顺序协作、业务状态如何变化、异常分支如何处理。

多校预约与时空调度系统的行为复杂度主要来自时段冲突、权限差异、状态变更和通知联动。学生预约场地需要完成可用性查询、预约提交、冲突检测、记录写入和结果反馈；管理员锁定时段则需要额外处理受影响预约、批量取消、审计记录和通知推送。本报告通过顺序图、通讯图、状态图和活动图，把这些行为过程展开说明，验证系统交互是否完整、清晰、可实现。

## 一. 实验目的

本实验旨在运用UML动态建模方法，对多校体育场地预约与时空调度子系统的运行时行为进行全面的动态描述。主要目标如下：

1. 掌握UML顺序图的绘制方法，描述对象间交互的消息传递与时间顺序。
2. 掌握UML通讯图的绘制，从空间协调角度描述对象间的消息传递关系。
3. 掌握UML状态图的绘制，刻画核心对象（Reservation）在生命周期中的状态变化与转移条件。
4. 掌握UML活动图的绘制，描述业务流程中的动作序列、分支逻辑与并行操作。
5. 通过多种动态视图完整描述系统的运行时行为，为代码实现提供精确的交互模型。

## 二. 实验内容

本实验运用UML动态建模技术对子系统一的核心业务流程和对象交互进行建模。通过顺序图绘制"学生预约场地"和"管理员锁定时段"两个核心场景；通过通讯图从空间协调角度展示对象间的消息传递；通过状态图刻画Reservation对象的生命周期状态变迁；通过活动图以四泳道形式展示学生预约的完整业务流程及并行/分支逻辑。

### 实验过程补充说明

本实验在前四次实验形成的需求模型、结构化模型、用例模型和静态模型基础上，进一步检查系统运行时的交互过程。动态建模关注"谁在什么时刻向谁发送消息、对象状态如何变化、流程分支如何结束"，因此本实验选择学生预约场地和管理员锁定时段作为核心场景。前者代表最常见的用户预约链路，后者代表具有较高权限和冲突影响的管理链路，二者能够覆盖普通预约、权限校验、冲突检测、状态写入、批量取消和通知触发等关键行为。

顺序图建模采用"参与对象识别—消息顺序排列—同步/异步区分—返回结果补充—异常分支检查"的步骤。学生预约场景中，消息从用户界面开始，依次经过控制器、业务服务、可用性校验、数据访问和通知模块；管理员锁定时段场景中，消息除了写入锁定记录，还需要查询受影响预约、批量更新预约状态、写入审计日志并触发通知。通过顺序图可以清楚表达控制流的先后关系和事务边界。

通讯图在顺序图基础上转换得到，重点不再强调时间轴，而是强调对象之间的协作网络。学生预约通讯图用于验证界面、控制器、服务、Mapper、数据库和通知模块之间是否存在必要连接；如果某个对象在通讯图中没有消息输入或输出，就说明它可能不是该场景的必要参与对象。通过通讯图检查，可以减少顺序图中过度建模或对象缺失的问题。

状态图用于刻画预约单从创建到结束的生命周期。状态变化必须与用例规格说明和结构化状态迁移图一致，例如预约单创建后进入待确认或已确认状态，随后可能因为用户取消、管理员锁定、超时未确认、正常使用完成而进入终态。状态图还用于检查非法转换，例如已完成预约不能再取消，已取消预约不能再次确认，管理员批量取消必须留下审计记录。

活动图用于描述业务流程中的条件判断和并行/分支路径。本实验围绕学生预约流程展示登录校验、场馆选择、时段查询、冲突检测、预约提交、结果反馈等步骤，并补充"无可用场地""预约冲突""取消后重新选择"等分支。通过活动图可以从用户操作角度验证流程是否闭环，也为后续测试用例设计提供步骤依据。

## 三. 实验步骤和结果

### 1. 顺序图

#### 1.1 场景一：学生预约场地

**场景描述：** 学生登录系统后，通过Reservation.vue页面选择场馆、日期与时段，提交预约请求。系统经历前端验证→后端Controller→Service→Mapper→MySQL的完整调用链，最终返回预约成功结果。

**参与对象：** 学生(用户)、Reservation.vue(前端)、ReservationController(控制层)、ReservationServiceImpl(业务层)、MySQL/ReservationMapper(数据层)

**消息交互序列：**

| 序号 | 调用方 | 被调方 | 消息 | 说明 |
|------|--------|--------|------|------|
| 1 | 学生 | Reservation.vue | 选择场馆+日期 | 用户操作 |
| 2 | Reservation.vue | ReservationController | GET schedule | 获取时段可用性网格 |
| 3 | Controller | Vue | 返回可用性数据 | 绿色/灰色时段网格 |
| 4 | 学生 | Vue | 选择时段+确认 | 用户选择 |
| 5 | Vue | Controller | POST create(RCR) | 提交预约请求 |
| 6 | Controller | ServiceImpl | createReservation() | 委托业务层 |
| 7 | ServiceImpl | (自调用) | 校验时间有效性 | start<end, end不在过去 |
| 8 | ServiceImpl | VenueOpsService | evaluateAvailability() | 检测教学占场与锁定 |
| 9 | ServiceImpl | Mapper/MySQL | SELECT冲突检测 | 同场馆同时段查询 |
| 10 | MySQL | ServiceImpl | 返回空集(无冲突) | 查询结果 |
| 11 | ServiceImpl | Mapper/MySQL | INSERT INTO t_reservation | 乐观锁写入 |
| 12 | MySQL | ServiceImpl | 插入成功 | 返回id |
| 13 | ServiceImpl | Controller | ApiResponse.success | 成功响应 |
| 14 | Controller | Vue | JSON响应 | HTTP 200 |
| 15 | ServiceImpl | NotificationService | 异步通知 | 预约确认 |

**时序特点：**
- 前端到后端为HTTP/JSON请求响应模式。
- 后端Service层串行执行校验→可用性检测→冲突检测→保存四步。
- 乐观锁机制在INSERT时通过版本号防并发冲突。
- 通知推送为异步操作，不阻塞主响应流。

#### 1.2 场景二：管理员锁定时段

**场景描述：** 管理员登录管理后台，通过AdminManage.vue选择目标场馆、设定锁定时段范围与原因，系统在数据库事务中插入锁定记录、批量取消冲突预约、写入审计日志，并异步通知受影响用户。

**参与对象：** 管理员、AdminManage.vue、ReservationController、ReservationServiceImpl、MySQL

**关键消息序列：**

| 序号 | 调用方 | 被调方 | 消息 | 说明 |
|------|--------|--------|------|------|
| 1 | 管理员 | AdminManage.vue | 进入时段锁定页面 | 管理后台 |
| 2 | 管理员 | Vue | 选择场馆+时段+原因 | 表单操作 |
| 3 | Vue | Controller | PUT lockVenueSlots | 锁定请求 |
| 4 | Controller | ServiceImpl | lockVenueSlots() | 委托业务层 |
| 5 | ServiceImpl | (自调用) | 验证时段+权限 | 业务校验 |
| 6 | ServiceImpl | MySQL | INSERT t_lock_record | 写入锁定记录 |
| 7 | MySQL | ServiceImpl | 写入成功 | 返回确认 |
| 8 | ServiceImpl | MySQL | UPDATE t_reservation SET CANCELLED | 批量取消冲突预约 |
| 9 | MySQL | ServiceImpl | 更新成功 | 返回影响行数 |
| 10 | ServiceImpl | MySQL | INSERT t_audit_log | 审计日志 |
| 11 | MySQL | ServiceImpl | 写入成功 | 审计完成 |
| 12 | ServiceImpl | Controller | ApiResponse.success | 成功响应 |
| 13 | ServiceImpl | NotificationService | 异步通知 | 受影响用户收到消息 |

**数据库事务保证：** 步骤6-10在一个MySQL事务中执行，任一步骤失败则整体回滚，确保数据一致性。

### 3. 状态图

**建模对象：** Reservation（预约单）的生命周期状态机。

**状态定义：**

| 状态 | 说明 | 入口动作 | 出口动作 |
|------|------|----------|----------|
| **PENDING** | 待确认 | entry/写入数据库 | — |
| **CONFIRMED** | 已确认 | entry/通知用户 | — |
| **COMPLETED** | 已完成 | — | — |
| **CANCELLED** | 已取消 | — | exit/释放时段 |

**状态迁移规则：**

| 源状态 | 目标状态 | 触发事件 | 动作 |
|--------|----------|----------|------|
| (初始) | PENDING | 提交预约 | INSERT t_reservation |
| PENDING | CONFIRMED | 系统确认 | 发送通知 |
| PENDING | CANCELLED | 用户取消（提前≥2小时） | 释放时段 |
| PENDING | CANCELLED | 超时取消 | 释放时段 |
| CONFIRMED | COMPLETED | 时间到达 | 标记完成 |
| CONFIRMED | CANCELLED | 管理员取消 | 释放时段+通知 |
| CONFIRMED | CANCELLED | 场馆锁定 | 释放时段+通知 |

### 4. 活动图

**建模场景：** 学生预约场馆的完整业务流程（带泳道）。

**泳道划分：**

| 泳道 | 参与者 | 负责活动 |
|------|--------|----------|
| **学生** | Student | 进入页面、选择场馆、选择日期、选择时段 |
| **前端** | Reservation.vue | 检索场馆列表、加载时段网格、渲染可视化、提交请求、显示结果 |
| **后端** | Spring Boot | 查询时段可用性、校验身份权限、冲突检测与乐观锁、返回预约详情 |
| **数据库** | MySQL | SELECT查询、INSERT事务写入 |

**流程控制逻辑：**

1. **开始** → 学生进入预约页面。
2. **Fork节点①（并行分叉）**：进入页面后，系统产生两条并行分支——
   - **分支1：** 前端向后台发起GET /api/venues请求，异步加载场馆列表数据。
   - **分支2：** 前端初始化页面框架与基础组件渲染。
   **Join节点①（同步汇合）**：场馆列表数据返回后两分支汇合。
3. 学生选择目标场馆，选择预约日期。
4. 前端请求后端查询时段可用性 → 渲染16格时段网格。
5. 学生选择连续时段后点击"确认预约"。
6. **决策节点**：[后端冲突检测结果]？
   - [有冲突] → 前端提示"时段已被占用" → 返回重新选择。
   - [无冲突] → 进入下一步。
7. 后端执行乐观锁INSERT写入数据库 → 事务提交成功。
8. **Fork节点②（并行分叉）**：
   - **分支1：** 后端返回成功给前端，渲染预约成功页面。
   - **分支2：** 异步触发NotificationService，推送预约确认通知。
9. **Join节点②**：所有分支完成后，流程结束。

**并行逻辑分析：**

| 并行节点 | 分支1 | 分支2 | 汇合点 |
|---------|-------|-------|--------|
| Fork①：学生进入预约页面后 | 前端加载场馆列表 | 前端初始化页面组件渲染 | Join①：场馆列表返回后汇合 |
| Fork②：预约写入成功后 | 后端返回预约详情至前端 | 异步推送确认通知 | Join②：通知发送完成后结束 |

## 四. 实验总结

### 实验中遇到的问题

1. **顺序图消息编号与嵌套调用的表达**：在顺序图中，Service层的自调用步骤（如时间有效性校验）与外部调用步骤（如VenueOpsService.evaluateAvailability()）的交错表达容易造成消息序列编号混乱。

2. **通讯图与顺序图的等价转换**：将顺序图转换为通讯图时，消息编号需要重新组织为层次化编号体系，容易出现编号不一致的问题。

3. **活动图泳道的职责划分**：前端异步加载场馆列表与页面初始化的并行活动属于不同泳道，但两条并行分支在时间上存在依赖关系，在活动图中准确表达这种跨泳道的同步汇合有一定难度。

### 解决方法

1. **自调用消息的表达规范**：对自调用步骤采用"对象自身的操作"图标（在生命线上的方框内标注），不占用消息箭头编号，仅在步骤说明中标注。外部调用则使用完整的消息箭头并分配顺序编号。这样既区分了两种调用类型，又保持了消息序列的清晰性。

2. **层次化消息编号体系**：采用"主序号.子序号"的层次化编号规则，如第5步"POST create(RCR)"的后续子步骤编号为5.1、5.1.1、5.1.2等，确保编号既能表达消息间的前后顺序，又能体现调用嵌套关系。

3. **跨泳道同步的显式表达**：采用"Fork→Join"控制节点对来显式表达并行与同步。在活动图中明确标注Fork节点的分叉条件和Join节点的汇合条件，确保跨泳道的并行活动正确同步。

### 思考与收获

通过本次动态建模与系统交互实践，完成了多校体育场地预约与时空调度子系统的全面动态行为建模。主要收获如下：

1. **顺序图建模**：为两个核心场景（学生预约、管理员锁定）绘制了完整的UML顺序图，明确标注了同步/异步消息、自调用校验步骤、乐观锁并发控制等关键交互。

2. **通讯图转换**：将顺序图转换为通讯图，以对象间链接关系为核心视角，通过层次化编号消息体系完整表达了多对象间的消息传递协调。

3. **状态图设计**：为Reservation对象设计了包含四种状态、六种迁移路径的完整状态机，明确标注了每种状态的entry/exit动作以及每个迁移的触发事件。

4. **活动图设计**：以四泳道（学生/前端/后端/数据库）划分了学生预约的完整业务流程，包含Fork节点（并行分叉）与Join节点（同步汇合）、决策节点（带Guard守卫条件的分支判断），完整刻画了业务操作序列、并行处理与分支逻辑。

五种动态建模视图从时间交互、空间协调、状态转移、业务流程四个维度全面刻画了系统的运行时行为，为后续的代码实现和测试用例设计提供了精确的交互契约和流程规范。
