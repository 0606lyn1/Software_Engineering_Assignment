# 实验报告五：动态建模与系统交互实践

**实验名称：** 实验五 动态建模与系统交互实践

**子系统：** 子系统一——多校体育场地预约与时空调度子系统

**对应代码：** `Reservation.vue` → `ReservationController` → `ReservationServiceImpl` → `VenueOpsServiceImpl`

---

## 报告说明

本报告从运行时行为角度描述子系统一两个核心场景的交互过程：学生创建预约、管理员/运维通过子系统二闭馆阻断预约。所有消息序列均对照实际源码调用链，修正原报告中不存在的 `GET schedule`、`lockVenueSlots`、`NotificationService` 等对象。

## 一. 实验目的

1. 掌握顺序图绘制，描述对象间消息传递与时间顺序。
2. 掌握通讯图绘制，展示对象协作拓扑。
3. 掌握状态图绘制，刻画预约对象生命周期。
4. 掌握活动图绘制，描述业务流程分支逻辑。

## 二. 实验内容

针对"学生创建预约"和"场地闭馆阻断预约"两个场景绘制顺序图与通讯图；绘制 Reservation 简化状态图；以四泳道活动图展示预约业务流程。

### 4. 活动图

**场景：** 学生创建预约（四泳道）

| 泳道 | 活动 |
| --- | --- |
| 学生 | 登录 → 进入预约页 → 选择场馆与时间 → 点击提交 |
| 前端 (Vue) | 加载场馆列表 → 客户端时间校验 → 发送 POST 请求 → 显示结果/跳转 |
| 后端 (Spring) | JWT 鉴权 → 获取 userId → createReservation() 四步校验 → 返回响应 |
| 数据库 (MySQL) | SELECT 重叠检测 → INSERT t_reservation |

**决策节点：**
- [start < end?] → 否：前端警告返回
- [available?] → 否：后端返回"场地暂不可预约"
- [用户重叠?] → 是：后端返回"预约冲突"
- [全部通过] → INSERT 成功

## 四. 实验总结

### 实验中遇到的问题

原报告场景二描述 `INSERT t_lock_record`、批量取消、审计日志、异步通知等流程，在当前代码中均不存在。

### 解决方法

将场景二改为"运维闭馆 → 预约阻断"的真实链路，保留原顺序图文件名但更新文字描述与之对齐。

### 思考与收获

动态建模是验证静态模型和用例规格的关键步骤。通过逐步追踪 `createReservation()` 的 7 次方法调用，确认了子系统一与子系统二之间的同步依赖关系，也为集成测试提供了可执行的交互契约。
