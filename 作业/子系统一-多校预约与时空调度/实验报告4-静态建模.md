# 实验报告四：静态建模实践

**实验名称：** 实验四 静态建模实践

**子系统：** 子系统一——多校体育场地预约与时空调度子系统

---

## 一、实验目的

本实验旨在运用UML静态建模方法，对多校体育场地预约与时空调度子系统进行系统的静态结构建模。主要目标如下：

1. 掌握UML类图的绘制方法，正确定义类的属性、方法及类间关系（关联、泛化、依赖、实现）。
2. 掌握UML对象图的绘制，以具体场景实例展示对象间的链接关系与属性值。
3. 掌握UML包图的绘制，清晰展示系统的包组织结构与包间依赖关系。
4. 掌握UML构件图与部署图的绘制，描述系统的物理组成与部署架构。
5. 通过多种静态建模视图全面刻画系统的静态结构。

## 五、构件图

系统由以下核心构件组成：

| 构件 | 类型 | 说明 |
|------|------|------|
| **WebApp** | 前端构件 | Vue 3 SPA，包含预约/场馆管理/用户管理等页面，通过Axios HTTP Client调用后端API |

## 六、部署图

系统采用多校多租户部署架构，每个学校独立部署MySQL数据库实例，共享同一套Spring Boot应用服务。

### 部署节点规划

| 节点 | 类型 | 配置 | 部署内容 |
|------|------|------|----------|
| **浏览器 Chrome/Edge** | device | 任意 | 学校A用户的Vue SPA前端 |
| **浏览器 Safari/Firefox** | device | 任意 | 学校B用户的Vue SPA前端 |
| **Nginx v1.26** | server | CPU:2核, RAM:4GB | 反向代理、SSL终端、负载均衡、静态资源缓存 |
| **Spring Boot App** | server | CPU:4核, RAM:8GB, Java 17 JVM | Spring Boot 3.4.4后端应用 |
| **MySQL 学校A** | database | CPU:2核, RAM:4GB | 学校A独立数据库(tenant_id='scu') |
| **MySQL 学校B** | database | CPU:2核, RAM:4GB | 学校B独立数据库(tenant_id='nju') |
| **DeepSeek API** | external | 云端SaaS | 推荐算法外部服务 |

### 网络拓扑
- 用户浏览器 → **HTTPS(443)** → Nginx
- Nginx → **HTTP(8080)** → Spring Boot App
- Spring Boot App → **JDBC(3306)** → MySQL(学校A)/MySQL(学校B)
- Spring Boot App → **HTTPS** → DeepSeek API（外部调用）

## 七、静态建模结果优化分析

### 7.1 类设计评估：内聚性与耦合性分析

| 评估维度 | 分析 | 评价 |
|----------|------|------|
| **类内聚性** | ReservationServiceImpl集中承担了预约校验、冲突检测、乐观锁写入等全部预约相关逻辑，职责高度内聚但单一类负担较重 | 高内聚，可考虑按职责进一步拆分 |
| **Controller-Service解耦** | Controller仅负责请求路由与参数绑定，不包含业务逻辑，通过接口依赖Service，符合依赖倒置原则 | 低耦合，设计良好 |
| **Service-Mapper依赖** | ServiceImpl直接依赖Mapper接口进行数据访问，未通过Repository层间接访问 | 中度耦合，MyBatis-Plus约定可接受 |
| **VenueOpsService依赖** | ReservationServiceImpl依赖VenueOpsService进行场馆可用性评估，两个Service之间形成协作依赖 | 合理耦合，职责划分清晰 |
| **实体与DTO分离** | Reservation实体类与ReservationCreateRequest DTO分离，避免API层暴露数据库模型 | 低耦合，符合分层规范 |

**优化建议：**
- 可将冲突检测逻辑从ReservationServiceImpl中抽取为独立的ConflictDetectionService，进一步提升单一职责与可测试性。
- 在Service接口层增加更多细粒度方法定义，避免Controller直接调用过于泛化的Service方法。

### 7.2 包结构优化建议

| 当前设计 | 优化建议 | 理由 |
|----------|----------|------|
| 所有Service接口集中在`service`包 | 建议按业务域拆分子包：`service.reservation`、`service.venue`、`service.user` | 避免包内类过多导致维护困难 |
| entity包包含所有实体 | 保持现状，实体类数量有限且关联紧密 | 当前设计已合理 |
| common包包含ApiResponse与PageResponse | 建议将PageResponse移至独立的`common.pagination`子包 | 区分通用响应与分页专用响应 |
| 缺少独立的`config.tenant`包 | 建议新增用于多租户配置类 | 多租户隔离是核心关注点，独立配置包更清晰 |

**优化后的包结构：**

com.example.tiyu

│   ├── venue
│   └── user
├── service

### 7.3 部署优化考虑

#### 缓存策略

| 缓存对象 | 建议方案 | 说明 |
|----------|----------|------|
| 场馆列表与类型 | Redis缓存，TTL=5分钟 | 场馆信息变更频率低，缓存可大幅减少数据库查询 |
| 时段可用性网格 | Redis缓存，TTL=30秒 | 可用性数据对实时性要求较高，短TTL缓存同时兼顾性能与准确性 |
| 用户认证Token | JWT无状态，无需服务端缓存 | 当前设计已是最优 |
| 推荐列表结果 | Redis缓存，TTL=10分钟 | 推荐结果可接受一定延迟，长TTL提升响应速度 |

#### 负载均衡

- Nginx作为反向代理入口，采用轮询（round-robin）策略分发请求至多个Spring Boot实例。
- 会话保持：由于采用JWT无状态认证，无需session粘滞，任意实例均可处理任意请求。
- 多校场景下，Nginx可根据请求URL中的租户标识进行一致性哈希路由，将同一学校的请求定向至同一实例以利用本地缓存。

#### 数据库优化

- 预约表的venue_id + start_time + end_time建立复合索引，加速冲突检测查询。
- 分表策略：预约表可按tenant_id进行水平分表，避免单表数据量过大。
- 读写分离：主库负责预约写入（INSERT/UPDATE），从库负责查询（SELECT），通过MySQL主从复制同步。

### 7.4 对建模结果的持续改进方向

1. **领域驱动设计演进**：当前类设计以数据模型为中心，后续可向DDD方向演进，引入Repository仓储模式替代Mapper的直接依赖，以及Domain Service处理复杂业务规则。

2. **异步与事件驱动**：预约成功后的通知推送、审计日志写入等可改为事件驱动架构（Spring Event / RabbitMQ），进一步降低核心预约流程的响应延迟。

3. **缓存一致性维护**：引入缓存失效机制——当预约创建、取消或场馆锁定事件发生时，主动清除或更新相关缓存条目，确保缓存与数据库的一致。

4. **多租户扩展**：当前部署图按数据库实例隔离租户，后续可演进为按Schema隔离（同实例不同Schema）或按表字段隔离（共享表+tenant_id过滤），以适应不同规模学校的部署需求。

5. **API版本管理**：随系统迭代引入API版本策略（URI路径版本或请求头版本），确保向后的接口兼容性。

## 八、实验总结

通过本次静态建模实践，完成了多校体育场地预约与时空调度子系统的全面静态结构建模。主要收获如下：

1. **类图设计**：识别了8个核心类（ReservationController/ReservationService/ReservationServiceImpl/Reservation/ReservationMapper/ReservationCreateRequest/ApiResponse/VenueOpsService），明确定义了每个类的属性与方法，并通过依赖、实现、泛化、关联四种关系完整描述了类间的静态耦合。

2. **对象图实例化**：以"张三预约篮球场"的具体场景为驱动，绘制了5个对象实例及其链接关系图，展示了从User到Reservation、Venue到Reservation的实例级引用。

3. **包图组织**：将11个子包按分层架构组织，清晰展示了controller→service→service.impl→mapper→entity的纵向依赖链，为代码工程化组织提供了蓝图。

4. **构件图与部署图**：从软件构件和物理部署两个维度描述了系统的组成与分布。构件图展示了WebApp/API Server/Database/Auth/DeepSeek API五大构件及其依赖；部署图展示了多校多租户的物理部署架构——共享Nginx+App Server，每校独立MySQL实例。

5. **建模结果优化分析**：对类设计进行了内聚性与耦合性评估，提出了包结构拆分与子包划分建议，从缓存策略、负载均衡、数据库索引与分表三个角度给出了部署优化建议，并指出了领域驱动设计演进、事件驱动架构、缓存一致性维护等持续改进方向。

静态建模为后续的动态建模（顺序图、通讯图、状态图、活动图）提供了完整的类结构基础。
