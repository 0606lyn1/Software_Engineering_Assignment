# 实验报告4——静态建模实践

**实验名称：** 实验四 静态建模实践

**子系统：** 子系统二——场地运维与公众监督子系统

---

## 一、实验目的

本实验旨在运用UML静态建模技术对子系统二进行全面的结构建模。通过绘制类图（Class Diagram）展示核心类的属性、方法和类间关系（关联、泛化、依赖、实现）；通过对象图（Object Diagram）展示某一时刻的对象实例快照；通过包图（Package Diagram）组织系统的包结构和依赖关系；通过构件图（Component Diagram）描述系统的软件构件组成；通过部署图（Deployment Diagram）展示系统的物理部署架构。通过本实验掌握面向对象静态建模的方法论。

## 二、类图（Class Diagram）

类图是子系统二的静态结构核心，涵盖控制器（Controller）、服务接口（Service）、服务实现（ServiceImpl）、实体（Entity）、数据传输对象（DTO）五个层次。

### 2.1 实体层

**VenueOps（场地运维信息实体）**：
- 属性：`id: Long`（主键）、`venueId: Long`（外键，关联 t_venue）、`maintenanceStatus: Enum`（NORMAL/MAINTENANCE）、`cleaningStatus: Enum`（QUALIFIED/PENDING_RECTIFICATION）、`lightingStatus: Enum`（NORMAL/PARTIAL_FAULT/FULL_FAULT）、`reservationPolicy: Enum`（FORBIDDEN/ALLOW_WITH_WARNING）、`responsibleName: String`、`responsibleRole: String`、`responsiblePhone: String`、`equipmentPolicy: String`、`selfEquipmentRequired: Boolean`、`selfEquipmentList: String`、`lastCleanedAt: LocalDateTime`、`lastInspectedAt: LocalDateTime`、`updatedAt: LocalDateTime`
- 方法：标准的 getter/setter 方法，由 Lombok `@Data` 或 `@Getter/@Setter` 自动生成

**Comment（评论实体）**：
- 属性：`id: Long`（主键）、`userId: Long`（外键，关联 t_user）、`venueId: Long`（外键，关联 t_venue）、`rating: Integer`（1-5）、`content: String`（max 500）、`status: String`（PUBLISHED/HIDDEN/DELETED）、`createdAt: LocalDateTime`、`updatedAt: LocalDateTime`
- 方法：getter/setter + 业务相关方法如 `isVisible()` 判断对用户是否可见

### 2.2 服务层

**VenueOpsService（接口）**：
- 方法：`getOrCreateByVenueId(Long venueId): VenueOps`（获取或自动创建）、`updateByVenueId(VenueOpsUpdateRequest req): void`（管理员更新）、`evaluateAvailability(Long venueId): VenueAvailabilityResponse`（可用性评估）、`getById(Long id): VenueOps`、`maskPhone(String phone, String role): String`（电话脱敏）

**CommentService（接口）**：
- 方法：`listLatest(Long venueId, String keyword): List<Comment>`（含用户名join查询）、`validateBeforeCreate(Long userId, Long venueId, String content): void`（校验）、`create(CommentCreateRequest req): Comment`、`deleteById(Long id, Long userId): void`、`filterSensitiveWords(String text): boolean`

**VenueOpsServiceImpl**：实现 `VenueOpsService` 接口，继承 MyBatis-Plus `ServiceImpl<VenueOpsMapper, VenueOps>`。通过 `SecurityContextHolder` 获取当前用户角色以判断电话脱敏策略。

**CommentServiceImpl**：实现 `CommentService` 接口，继承 `ServiceImpl<CommentMapper, Comment>`。包含 `checkSpam()` 私有方法（60秒冷却检测）和 `filterSensitiveWords()`（遍历配置词库的包含匹配）。

### 2.3 控制层与DTO

**VenueOpsController**：
- `GET /api/venue-ops/{venueId}`：获取运维信息（非管理员电话脱敏）
- `PUT /api/venue-ops/{venueId}`：管理员更新运维配置
- `GET /api/venue-ops/{venueId}/availability`：场地可用性查询

**CommentController**：
- `GET /api/comments`：评论列表查询（支持 venueId 和 keyword 参数）
- `POST /api/comments`：发表评论（@Valid 校验）
- `DELETE /api/comments/{id}`：删除评论（作者或管理员权限）

**VenueAvailabilityResponse（DTO）**：`reservable: boolean`、`reasonCode: String`（如"MAINTENANCE"/"CLEANING_FAIL"/"LIGHTING_FAULT"/"OK"）、`displayMessage: String`、`maintenanceFlags: List<String>`

**VenueOpsUpdateRequest（DTO）**：所有字段均为可选（Optional），允许管理员仅修改特定字段而不影响其他属性。

**CommentCreateRequest（DTO）**：`venueId: Long (@NotNull)`、`rating: Integer (@Min(1) @Max(5))`、`content: String (@Size(max=500))`

### 2.4 类间关系

1. **依赖**：`VenueOpsController` 通过 `@Autowired` 依赖注入 `VenueOpsService` 实例。`CommentController` 同理依赖 `CommentService`。
2. **实现**：`VenueOpsServiceImpl` 实现 `VenueOpsService` 接口。`CommentServiceImpl` 实现 `CommentService` 接口。
3. **泛化**：两个 ServiceImpl 均继承 MyBatis-Plus 的 `ServiceImpl<M extends BaseMapper<T>, T>` 基类，获得内置的 `save()`、`getById()` 等 CRUD 方法。
4. **使用**：Service 层使用 Entity 实体进行数据持久化操作，使用 DTO 进行数据传输。Service 返回 `VenueAvailabilityResponse` 给 Controller，Controller 接收 `VenueOpsUpdateRequest` 和 `CommentCreateRequest` 作为请求体参数。

## 三、对象图（Object Diagram）

以"保洁李四于2026-05-10 14:00完成篮球场清洁打卡"为场景快照，展示以下对象实例及其链接：

- **basketballCourt: t_venue**（id=101, name="篮球场1号", type="OUTDOOR_BASKETBALL", is_outdoor=true, status="ACTIVE"）
- **ops_basketball: t_venue_ops**（id=201, venueId=101, maintenanceStatus=NORMAL, cleaningStatus=QUALIFIED, lightingStatus=NORMAL, reservationPolicy=ALLOW_WITH_WARNING, responsibleName="王五", lastCleanedAt=2026-05-10 14:00, updatedAt=2026-05-10 14:00）
- **log_20260510: t_cleaning_log**（id=301, venueId=101, cleanerId=502, cleanResult="合格", cleanNotes="已完成清洁", photoUrl=null）
- **cleaner_li: t_user**（id=502, username="cleaner_li", role=ROLE_CLEANER, phone="13612345678", realName="李四"）
- **availabilityResp: VenueAvailabilityResponse**（reservable=true, reasonCode="OK", displayMessage="场地可预约"）

对象之间的链接关系：basketballCourt 与 ops_basketball 为1:1链接（venue_id关联），ops_basketball 与 log_20260510 为1:N链接，cleaner_li 与 log_20260510 为执行关系，ops_basketball 通过 `evaluateAvailability()` 生成 availabilityResp 快照。

## 四、包图（Package Diagram）

系统根包为 `com.example.tiyu`，包含以下子包：

1. **controller**（控制层包）：包含 `VenueOpsController`、`CommentController`、`AdminController`、`VenueController`，均标注 `@RestController` 注解。依赖 service 包。

2. **service**（服务层包）：包含 `«接口» VenueOpsService`、`«接口» CommentService`、`VenueOpsServiceImpl`、`CommentServiceImpl`，均标注 `@Service` 注解。依赖 entity 包和 mapper 包。

3. **entity/model**（实体包）：包含 `VenueOps`、`Comment`、`Venue`、`User`、`CleaningLog` 等 MyBatis-Plus 实体类。被 service 包和 controller 包引用。

4. **dto**（数据传输对象包）：包含 `VenueOpsUpdateRequest`、`VenueAvailabilityResponse`、`CommentCreateRequest`、`ApiResponse<T>` 等请求/响应DTO。在 controller 和 service 层之间传递数据。

5. **mapper**（持久层包）：包含 `VenueOpsMapper`、`CommentMapper`，继承 MyBatis-Plus `BaseMapper<T>`。被 service 包调用，通过 JDBC 访问数据库。

6. **config**（配置包）：包含 `SecurityConfig`、`JwtConfig`、`MyBatisPlusConfig`，标注 `@Configuration` 注解。被 controller 包和 service 包依赖，提供安全策略和数据源配置。

包间依赖关系呈现自上而下的分层结构：`controller → service → mapper → entity`，`dto` 横向贯穿各层，`config` 提供横切关注点注入。

## 五、构件图（Component Diagram）

构件图展示子系统二的软件构件组成及其接口：

### 前端构件（Vue 3 + TypeScript）

- **VenueList.vue**：场地列表展示，提供运维状态标签（颜色编码）和"查看评论"入口。
- **CommentList.vue**：可复用评论组件，提供评论列表展示、发表表单、关键词搜索和删除操作。
- **AdminManage.vue**：管理员运维配置页面，通过"运维"按钮弹窗配置所有 `VenueOps` 属性。
- **Pinia Store**：全局状态管理，存储 JWT Token、用户信息、当前场地数据。

前端构件通过 Axios HTTP Client 与后端 REST API 进行通信，数据格式为 JSON。

### 后端构件（Spring Boot 3.4.4）

- **VenueOpsController**：提供 `/api/venue-ops/**` REST API
- **CommentController**：提供 `/api/comments/**` REST API
- **VenueOpsService / VenueOpsServiceImpl**：运维管理业务逻辑（可用性评估、电话脱敏）
- **CommentService / CommentServiceImpl**：评论管理业务逻辑（敏感词过滤、反刷屏检测）
- **VenueOpsMapper / CommentMapper**：MyBatis-Plus 数据访问层
- **Spring Security + JWT**：认证授权拦截器
- **application.yml**：运行时配置（敏感词列表、反刷屏冷却秒数）

### 数据构件（MySQL 8.4）

`t_venue_ops` 表和 `t_comment` 表，通过 JDBC/MyBatis 与后端构件通信。

### 外部系统构件

子系统一（场地预约子系统）通过调用 `GET /api/venue-ops/{venueId}/availability` 接口获取可用性数据。

## 六、部署图（Deployment Diagram）

部署架构包含五个节点：

1. **客户端节点（浏览器）**：运行 Vue 3 SPA 应用（Vite 构建产物 + Ant Design Vue UI），通过 HTTPS 协议与 Nginx 通信，Authorization Header 携带 JWT Bearer Token。

2. **反向代理节点（Nginx）**：提供 HTTP 负载均衡、SSL 终止和静态资源缓存，将请求转发到 Spring Boot 应用服务器（8080端口）。

3. **应用服务器节点（Spring Boot / JDK 17）**：运行嵌入式 Tomcat（port 8080），部署 `VenueOps模块`（REST /venue-ops/**）、`Comment模块`（REST /comments/**）和 `Security模块`（JWT Filter + CORS 配置）。配置项从 `application.yml` 加载：`comment.anti-spam-seconds=60`、`comment.sensitive-words` 词库。

4. **数据库服务器节点（MySQL 8.4）**：运行 `tiyu_db` 数据库，存储 `t_venue_ops`（运维信息）和 `t_comment`（评论数据）等表。通过 JDBC:3306 与应用服务器通信。

5. **辅助服务节点（Redis，可选）**：存储反刷屏缓存（60秒TTL per user-venue pair），JWT黑名单和会话管理数据。

外部系统子系统一通过 REST API 调用查询场地可用性，采用最终一致性策略。

## 七、实验总结

本实验完成了子系统二的五种静态建模视图。类图精确刻画了系统的领域模型——以 `VenueOps` 和 `Comment` 为核心实体，以 `VenueOpsService` 和 `CommentService` 为业务逻辑中枢，以 `VenueOpsController` 和 `CommentController` 为对外接口，通过依赖注入、接口实现和泛化继承建立起清晰的类间关系网。对象图以具体场景快照展示了运行时的对象实例结构，验证了类图设计的合理性。包图采用分层架构组织代码，实现了关注点分离（Controller/Service/Mapper/Entity/Config/DTO），依赖方向自顶向下。构件图展示了前端Vue组件、后端Spring服务、MySQL数据库和外部系统的完整软件构件体系。部署图从物理部署视角描述了客户端、代理、应用服务器、数据库和缓存节点的分布和通信协议。五种视图相互补充，共同构成了子系统二完整的静态架构模型。
