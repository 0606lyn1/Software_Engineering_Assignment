# 实验报告4——静态建模实践

**实验名称：** 实验四 静态建模实践

**子系统：** 子系统二——场地运维与公众监督子系统

---

## 报告说明

本报告面向子系统二的软件结构进行静态建模，重点说明场地运维与公众监督系统由哪些类、对象、包、构件和部署节点组成。前三次实验已经从需求、数据流和用例角度描述了系统，本实验进一步把这些分析结果转化为UML静态模型，使业务实体、服务职责、数据访问关系和部署结构更加清晰。

子系统二的静态结构需要同时支撑运维记录、公众评论、负责人待办、设备信息和可用性输出。评论、场地、用户、负责人、运维记录、灯光状态和器材信息之间存在稳定业务关系；控制层、服务层、Mapper层、DTO和外部接口对象之间也需要保持清晰职责边界。本报告通过类图、对象图、包图、构件图和部署图，从不同层次说明系统结构，并检查模型是否满足可维护、可追溯和跨系统联动要求。

## 一. 实验目的

本实验旨在运用UML静态建模技术对子系统二进行全面的结构建模。通过绘制类图（Class Diagram）展示核心类的属性、方法和类间关系（关联、泛化、依赖、实现）；通过对象图（Object Diagram）展示某一时刻的对象实例快照；通过包图（Package Diagram）组织系统的包结构和依赖关系；通过构件图（Component Diagram）描述系统的软件构件组成；通过部署图（Deployment Diagram）展示系统的物理部署架构。通过本实验掌握面向对象静态建模的方法论。

## 二. 实验内容

本实验运用UML静态建模技术对子系统二进行全面的结构建模。通过类图展示核心类的属性、方法和类间关系（VenueOps/Comment为核心实体，VenueOpsService/CommentService为业务逻辑中枢）；通过对象图展示"保洁李四清洁打卡"场景的对象实例快照；通过包图组织系统的分层包结构；通过构件图描述前端Vue组件、后端Spring服务、MySQL数据库和外部系统的软件构件体系；通过部署图展示客户端、代理、应用服务器、数据库和缓存节点的分布。

### 实验过程补充说明

本实验以需求规格说明、结构化分析模型和用例规格说明为输入，按照"核心实体识别—类职责划分—对象场景验证—包结构组织—构件关系设计—部署结构描述"的顺序进行。首先从ER图和用例规格中提取场地、评论、运维记录、负责人、灯光状态、器材信息、待办事项等核心业务对象，再根据系统分层补充控制类、服务类、数据访问类、DTO和统一响应类。

类图设计重点体现职责分离。控制类负责接收HTTP请求、进行参数绑定和响应封装；服务接口定义评论管理、运维管理、负责人管理和可用性评估能力；服务实现类负责内容校验、状态转换、负面反馈触发、评分统计和可用性计算；实体类映射数据库表；Mapper类负责持久化访问；DTO类用于隔离外部输入输出。通过这种设计，可以避免把评论审核、运维记录写入和可用性评估混在同一类中。

对象图用于验证类图是否能支撑具体业务场景。本实验选择"用户发表负面评论并生成负责人待办"作为典型对象快照，因为该场景同时涉及用户、场地、评论、负责人、待办事项和通知结果，能够检验类图中关联关系、属性字段和对象链接是否完整。若对象图中某个对象无法追溯到类图，说明类图仍需补充对应类型或关系。

包图、构件图和部署图从不同层次补充系统静态结构。包图用于展示控制层、服务层、实体层、Mapper层、DTO层和外部接口层之间的依赖方向；构件图用于描述前端页面、后端服务、数据库、评论审核模块、通知模块和可用性输出接口之间的协作；部署图用于说明服务器、数据库、缓存、客户端和外部子系统之间的物理连接关系。

建模完成后，本实验从一致性、扩展性和安全性三方面检查模型。类名和属性应与ER实体一致；服务依赖应遵循单向分层原则；评论审核策略、通知方式、可用性评估规则和设备状态来源应能够扩展；涉及用户评论和责任人处理记录的数据应具备权限控制和审计追踪能力。

## 三. 实验步骤和结果

### 1. 类图（Class Diagram）

类图是子系统二的静态结构核心，涵盖控制器（Controller）、服务接口（Service）、服务实现（ServiceImpl）、实体（Entity）、数据传输对象（DTO）五个层次。

#### 1.1 实体层

**VenueOps（场地运维信息实体）：**
- 属性：id, venueId, maintenanceStatus(Enum), cleaningStatus(Enum), lightingStatus(Enum), reservationPolicy(Enum), responsibleName, responsibleRole, responsiblePhone, equipmentPolicy, selfEquipmentRequired, selfEquipmentList, lastCleanedAt, lastInspectedAt, updatedAt
- 方法：标准的getter/setter方法，由Lombok @Data自动生成

**Comment（评论实体）：**
- 属性：id(PK), userId(FK), venueId(FK), rating(1-5), content(max 500), status(PUBLISHED/HIDDEN/DELETED), createdAt, updatedAt
- 方法：getter/setter + `isVisible()` 判断对用户是否可见

#### 1.2 服务层

**VenueOpsService（接口）：**
- 方法：`getOrCreateByVenueId(Long venueId): VenueOps`、`updateByVenueId(VenueOpsUpdateRequest req): void`、`evaluateAvailability(Long venueId): VenueAvailabilityResponse`、`getById(Long id): VenueOps`、`maskPhone(String phone, String role): String`

**CommentService（接口）：**
- 方法：`listLatest(Long venueId, String keyword): List<Comment>`、`validateBeforeCreate(Long userId, Long venueId, String content): void`、`create(CommentCreateRequest req): Comment`、`deleteById(Long id, Long userId): void`、`filterSensitiveWords(String text): boolean`

**VenueOpsServiceImpl：** 实现 `VenueOpsService` 接口，继承 MyBatis-Plus `ServiceImpl<VenueOpsMapper, VenueOps>`。

**CommentServiceImpl：** 实现 `CommentService` 接口，继承 `ServiceImpl<CommentMapper, Comment>`。包含 `checkSpam()` 和 `filterSensitiveWords()` 私有方法。

#### 1.3 控制层与DTO

**VenueOpsController：** GET /api/venue-ops/{venueId}（获取运维信息）、PUT /api/venue-ops/{venueId}（管理员更新）、GET /api/venue-ops/{venueId}/availability（场地可用性查询）

**CommentController：** GET /api/comments（评论列表查询）、POST /api/comments（发表评论）、DELETE /api/comments/{id}（删除评论）

**DTO类：** VenueAvailabilityResponse、VenueOpsUpdateRequest、CommentCreateRequest

#### 1.4 类间关系

1. **依赖**：Controller 通过 @Autowired 依赖注入 Service 实例。
2. **实现**：ServiceImpl 实现 Service 接口。
3. **泛化**：ServiceImpl 继承 MyBatis-Plus 的 `ServiceImpl<M, T>` 基类。
4. **使用**：Service 层使用 Entity 实体进行数据持久化操作，使用 DTO 进行数据传输。

### 3. 包图（Package Diagram）

系统根包为 `com.example.tiyu`，包含以下子包：

| 包名 | 职责 | 包含的主要类 |
|------|------|-------------|
| controller | 控制层 | VenueOpsController, CommentController |
| service | 服务层 | VenueOpsService, CommentService, VenueOpsServiceImpl, CommentServiceImpl |
| entity/model | 实体层 | VenueOps, Comment, Venue, User, CleaningLog |
| dto | 数据传输对象 | VenueOpsUpdateRequest, VenueAvailabilityResponse, CommentCreateRequest |
| mapper | 持久层 | VenueOpsMapper, CommentMapper |
| config | 配置层 | SecurityConfig, JwtConfig, MyBatisPlusConfig |

包间依赖关系呈现自上而下的分层结构：`controller → service → mapper → entity`，`dto` 横向贯穿各层，`config` 提供横切关注点注入。

### 4. 构件图（Component Diagram）

**前端构件（Vue 3 + TypeScript）：**
- **VenueList.vue**：场地列表展示，提供运维状态标签和"查看评论"入口。
- **CommentList.vue**：可复用评论组件，提供评论展示、发表、搜索和删除。
- **AdminManage.vue**：管理员运维配置页面。
- **Pinia Store**：全局状态管理。

**后端构件（Spring Boot 3.4.4）：**
- **VenueOpsController**：提供 `/api/venue-ops/**` REST API
- **CommentController**：提供 `/api/comments/**` REST API
- **VenueOpsService / VenueOpsServiceImpl**：运维管理业务逻辑
- **CommentService / CommentServiceImpl**：评论管理业务逻辑
- **VenueOpsMapper / CommentMapper**：MyBatis-Plus 数据访问层
- **Spring Security + JWT**：认证授权拦截器

**数据构件（MySQL 8.4）：** `t_venue_ops` 表和 `t_comment` 表。

**外部系统构件：** 子系统一通过调用 `GET /api/venue-ops/{venueId}/availability` 获取可用性数据。

### 5. 部署图（Deployment Diagram）

部署架构包含五个节点：

1. **客户端节点（浏览器）**：运行 Vue 3 SPA 应用，通过 HTTPS 协议与 Nginx 通信。
2. **反向代理节点（Nginx）**：提供 HTTP 负载均衡、SSL 终止和静态资源缓存。
3. **应用服务器节点（Spring Boot / JDK 17）**：运行嵌入式 Tomcat，部署运维模块和评论模块。
4. **数据库服务器节点（MySQL 8.4）**：存储运维信息和评论数据。
5. **辅助服务节点（Redis，可选）**：存储反刷屏缓存（60秒TTL per user-venue pair）。

## 四. 实验总结

### 实验中遇到的问题

1. **实体类的枚举字段表达**：VenueOps 包含四个枚举字段（maintenanceStatus、cleaningStatus、lightingStatus、reservationPolicy），在类图中如何简洁而清晰地表达这些枚举类型及其取值范围是一个挑战。

2. **ServiceImpl的泛化关系**：CommentServiceImpl 继承 MyBatis-Plus 的 `ServiceImpl<CommentMapper, Comment>`，泛型参数较多，在类图中如何正确表达这种带泛型参数的继承关系。

3. **对象图的场景真实性**：对象图需要基于真实场景数据，但在系统尚未实现的情况下，虚构的场景数据需要与类图的类定义严格对应，属性值不能超出类图中定义的属性范围。

### 解决方法

1. **枚举类型的紧凑表达**：采用 `<<enumeration>>` 构造型标注枚举类型，在类图中将枚举作为独立类列出，内部列出所有枚举值。VenueOps 类中直接引用枚举类型名，不展开枚举值，保持类图简洁。

2. **泛型参数的简化表达**：在类图中使用 `ServiceImpl<CommentMapper, Comment>` 的简化标注方式，省略完整的泛型参数声明。在注释中对 MyBatis-Plus 的泛型机制进行额外说明，解释 Mapper 和 Entity 的对应关系。

3. **场景驱动的对象图验证**：先写出完整的场景描述（谁、什么时间、做什么、产生什么数据），然后基于场景描述逐一验证每个对象实例的属性值是否符合类定义，确保对象图与类图的一致性。

### 思考与收获

本实验完成了子系统二的五种静态建模视图。类图精确刻画了系统的领域模型——以 `VenueOps` 和 `Comment` 为核心实体，以 `VenueOpsService` 和 `CommentService` 为业务逻辑中枢，以 `VenueOpsController` 和 `CommentController` 为对外接口。对象图以具体场景快照展示了运行时的对象实例结构，验证了类图设计的合理性。包图采用分层架构组织代码，实现了关注点分离。构件图展示了前端Vue组件、后端Spring服务、MySQL数据库和外部系统的完整软件构件体系。部署图从物理部署视角描述了客户端、代理、应用服务器、数据库和缓存节点的分布和通信协议。五种视图相互补充，共同构成了子系统二完整的静态架构模型。
