## 一. 实验目的

1. 识别子系统二参与者与用例。
2. 绘制 UML 用例图。

## 二. 实验内容

识别五类参与者，定义六个核心用例，撰写 UC-O1 至 UC-O4 规格说明。

### 3. 用例规格说明

#### UC-O1 填报场地运维状态

| 属性 | 内容 |
| --- | --- |
| **用例编号** | UC-O1 |
| **用例名称** | 填报场地运维状态 |
| **参与者** | 运维人员（STAFF）、管理员（ADMIN） |
| **简述** | 运维人员选择场馆，更新四维运维状态并保存 |
| **优先级** | 高 |

**前置条件：**
1. 用户已登录，角色为 ADMIN 或 STAFF。
2. 目标场馆存在于 t_venue 表。

**后置条件（成功）：**
1. t_venue_ops 记录更新四维状态。
2. lastInspector 设为当前 JWT 用户名。
3. lastCheckedAt 更新为当前时间。
4. 若清洁/维护状态变为阻断值，后续预约将被 getAvailability() 拒绝。

**基本事件流：**

| 步骤 | 动作 | 实现 |
| --- | --- | --- |
| 1 | 运维进入 /maintenance | VenueMaintenance.vue |
| 2 | 加载场馆列表和运维台账 | api.getVenues() + api.getVenueOps() |
| 3 | 选择目标场馆 | selectedVenueId |
| 4 | 加载详情和可约性 | api.getVenueOpsByVenue() + api.getVenueAvailability() |
| 5 | 填写四维状态+负责人+备注 | formState reactive |
| 6 | 点击保存 | api.updateVenueOps(venueId, formState) |
| 7 | 后端权限校验 | @PreAuthorize("ADMIN","STAFF") |
| 8 | 后端更新记录 | VenueOpsServiceImpl.updateOps() |
| 9 | 前端刷新可约性预览 | PASS/HOLD 标签更新 |

**异常事件流：**
- 场馆不存在 → "场馆不存在"
- 非 ADMIN/STAFF → 403 权限拒绝

#### UC-O2 查看场地运维状态

| 属性 | 内容 |
| --- | --- |
| **用例编号** | UC-O2 |
| **用例名称** | 查看场地运维状态 |
| **参与者** | 所有用户 |
| **简述** | 在场馆列表页查看各场地运维四维标签 |

**基本事件流：**
1. 用户进入 /venues（VenueList.vue）。
2. 调用 GET /api/venue-ops 获取全部运维记录。
3. 前端按 maintenanceStatus/cleaningStatus/lightingStatus 渲染颜色标签（红/橙/绿）。
4. 用户可点击"评论"按钮打开评论抽屉。

#### UC-O3 发表评论

| 属性 | 内容 |
| --- | --- |
| **用例编号** | UC-O3 |
| **用例名称** | 发表评论 |
| **参与者** | 登录用户（学生/教师/管理员） |
| **简述** | 用户对指定场馆发表文字评论 |

**前置条件：** 用户已登录（JWT 有效）。

**基本事件流：**
1. 用户在 VenueList 点击"评论"，打开 CommentList 抽屉。
2. 加载已有评论：GET /api/comments?venueId=。
3. 用户输入评论内容（前端 maxlength=200）。
4. 点击发表：POST /api/comments { venueId, content }。
5. CommentController 从 JWT 获取 userId，构造 Comment 并 save。
6. 刷新评论列表。

**异常事件流：**
- 未登录 → 路由守卫跳转 /login
- 内容为空 → 前端校验阻止提交

#### UC-O5 查询场地可约性

| 属性 | 内容 |
| --- | --- |
| **用例编号** | UC-O5 |
| **用例名称** | 查询场地可约性 |
| **参与者** | 子系统一（ReservationServiceImpl）、公开查询 |
| **简述** | 评估场地四维运维状态，返回是否可预约 |

**基本事件流：**
1. 调用方请求 GET /api/venue-ops/{venueId}/availability。
2. VenueOpsController.availability() 委托 getAvailability(venueId)。
3. getOrCreateByVenueId() 确保运维记录存在。
4. 按 maintenance → cleaning → lighting → equipment 顺序检测阻断。
5. 返回 VenueAvailabilityResponse { venueId, available, status, reason }。

**子系统一调用路径：**
ReservationServiceImpl.createReservation() 在 L31 同步调用，available=false 时抛出 BusinessException。

## 四. 实验总结

### 实验中遇到的问题

原用例规格引用了 CommentServiceImpl.validateBeforeCreate()、maskPhone()、AdminManage.vue 等不存在的方法和页面。

### 解决方法

用例事件流改为引用 VenueMaintenance.vue、CommentController.create()、VenueOpsServiceImpl.updateOps() 等实际代码路径。

### 思考与收获

用例 UC-O5（查询可约性）是子系统二与子系统一的关键契约，其规格说明直接决定了预约能否成功，体现了跨子系统用例建模的重要性。
