# 实验报告3——面向对象分析与设计实践

**实验名称：** 实验三 面向对象分析与设计实践

**子系统：** 子系统二——场地运维与公众监督子系统

---

## 一. 实验目的

本实验旨在运用面向对象分析方法对子系统二进行用例驱动的需求建模。通过识别系统参与者（Actor）与用例（Use Case），梳理用例与参与者、用例之间的关系（包含、扩展、泛化），绘制规范的UML用例图。在此基础上，针对四个核心用例撰写完整的用例规格说明，包含前置条件、后置条件、基本事件流和异常事件流。通过本实验掌握基于用例的面向对象分析方法。

## 二. 实验内容

本实验运用面向对象分析方法对子系统二进行用例驱动的需求建模。识别四类人类参与者和一个外部系统参与者，梳理七个核心用例及其关系，绘制UML用例图。针对UC-O1（保洁完成清洁打卡）、UC-O2（用户发表评论）、UC-O3（管理员处理违规评论）、UC-O4（负责人接收负面反馈待办）四个核心用例撰写完整的用例规格说明。

## 三. 实验步骤和结果

### 1. 参与者识别

子系统二共涉及五类参与者（Actor），其中四类为人类用户，一类为外部系统：

#### 1.1 普通用户（学生/教师）

泛化自"普通用户"角色，是系统的最大参与者群体。通过 `GET /api/venue-ops/{venueId}` 查看场地运维状态（电话脱敏），通过 `POST /api/comments` 发表评论，通过 `GET /api/comments` 搜索和浏览评论。

#### 1.2 运维保洁人员

负责场地的日常清洁、灯光检查和器材维护。通过清洁打卡接口更新 `t_venue_ops.cleaningStatus`，通过灯光记录接口更新 `lightingStatus`。其操作可能触发 `evaluateAvailability()` 可用性重算。该角色可泛化出清洁员、灯光检查员和器材管理员三个子角色。

#### 1.3 场地负责人

对特定场地负有管理责任。接收系统自动生成的负面反馈待办（UC-O4），查看负责场地的综合运维报表，协调维修并更新场地状态。

#### 1.4 管理员

系统最高权限用户。通过 `AdminManage.vue` 中的运维配置弹窗配置场地负责人和规则（`PUT /api/venue-ops/{venueId}`），处理违规评论（`DELETE /api/comments/{id}` 并记录审计日志），管理敏感词配置。

#### 1.5 子系统一（外部系统）

场地预约子系统，通过调用 `GET /api/venue-ops/{venueId}/availability` 接口获取场地的可预约状态，接收 `VenueAvailabilityResponse` 结构体。

### 2. 用例图

用例图将系统边界内的7个用例、5类参与者和它们之间的关联关系可视化。核心用例包括：

- **UC-O1 保洁完成清洁打卡**：由保洁运维人员发起，扩展触发可用性重算。
- **UC-O2 用户发表评论**：由普通用户发起，包含敏感词过滤和反刷屏子流程。
- **UC-O3 管理员处理违规评论**：由管理员发起，写入审计日志。
- **UC-O4 负责人接收负面反馈待办**：由系统检测低分评论自动生成，由负责人处理，若持续未处理则扩展升级通知管理员。
- 此外还包括"查看运维状态与器材""查询场地可用性""配置负责人与规则"等支撑用例。

### 3. 用例规格说明

#### UC-O1：保洁完成清洁打卡

**参与者：** 运维保洁人员

**前置条件：**
1. 保洁人员已通过 Spring Security + JWT 认证，拥有 `ROLE_CLEANER` 角色权限。
2. 该保洁人员已被分配至目标场地。
3. 当前时间在系统允许的保洁在岗时间范围内。

**后置条件：**
1. 成功：清洁记录保存到 `t_cleaning_log` 表；`t_venue_ops.cleaningStatus` 被更新；若清洁结果为 PENDING_RECTIFICATION 且配置禁止预约，场地可预约性状态更新为 NOT_RESERVABLE。
2. 失败：系统状态不变，向用户返回具体错误信息。

**基本事件流：**

| 步骤 | 描述 |
|------|------|
| 1 | 保洁人员登录系统，进入场地管理页面。 |
| 2 | 保洁人员选择目标场地。 |
| 3 | 系统展示当前场地的运维状态信息。 |
| 4 | 保洁人员点击"清洁打卡"按钮，系统弹出打卡表单。 |
| 5 | 保洁人员填写清洁时间、清洁检查结果、备注信息（可选）、现场照片（可选）。 |
| 6 | 保洁人员确认提交，系统创建清洁日志、更新运维状态、重新计算可预约性。 |
| 7 | 系统返回操作成功确认，显示更新后的运维状态。 |

**异常事件流：**
1. **重复打卡**：同一保洁人员在短时间内对同一场地重复打卡，返回提示。
2. **场地不存在**：venueId对应的场地不存在，返回404错误。
3. **权限不足**：当前用户角色不包含ROLE_CLEANER，返回403错误。
4. **网络异常**：前端显示"网络异常，请重试"，表单数据暂存本地。

#### UC-O2：用户发表评论

**参与者：** 普通用户（学生/教师）

**前置条件：**
1. 用户已通过 JWT 认证登录系统。
2. 目标场地存在于系统中。
3. 用户未被管理员禁言。

**后置条件：**
1. 成功：评论记录保存到 `t_comment` 表，评论状态为 PUBLISHED 并公开可见。
2. 失败：系统状态不变，用户收到错误提示。

**基本事件流：**

| 步骤 | 描述 |
|------|------|
| 1 | 用户登录系统，进入场地列表。 |
| 2 | 用户点击某个场地的"查看评论"按钮，前端打开抽屉加载 CommentList.vue。 |
| 3 | CommentList.vue 调用 GET /api/comments 获取已有评论列表。 |
| 4 | 用户在评论表单区域输入评分（1-5星）和评论内容（最多500字）。 |
| 5 | 用户点击"提交评论"，前端执行客户端校验。 |
| 6 | 后端执行反刷屏检测、敏感词过滤、重复内容检测。 |
| 7 | 校验通过后保存评论到数据库，返回201 Created。 |
| 8 | 前端刷新评论列表，新评论出现在列表顶部。 |
| 9 | 后端异步检查：若评分≤2，统计低分评论数量，超阈值则生成负责人待办。 |

**异常事件流：**
1. **敏感词拦截**：返回400错误"评论包含敏感词，请修改后重新提交"。
2. **刷屏限制**：返回429错误"请稍候60秒后再发表评论"。
3. **重复内容**：返回400错误"请勿重复发表相同内容"。
4. **场地不存在**：返回404错误。
5. **未登录**：返回401 Unauthorized。

#### UC-O3：管理员处理违规评论

**参与者：** 管理员

**前置条件：**
1. 管理员已通过 JWT 认证，拥有 `ROLE_ADMIN` 角色。
2. 存在需要处理的违规评论。

**基本事件流：**

| 步骤 | 描述 |
|------|------|
| 1 | 管理员登录系统，进入后台管理页面。 |
| 2 | 管理员在评论管理模块中查看标记为"待处理"的违规评论。 |
| 3 | 管理员查看违规评论的详细内容，确认违规事实。 |
| 4 | 管理员选择处理方式（隐藏评论或删除评论）。 |
| 5 | 系统弹出确认对话框，要求填写操作原因。 |
| 6 | 管理员确认操作，系统更新评论状态并写入审计日志。 |
| 7 | 系统返回操作成功确认。 |

**异常事件流：**
1. **评论不存在**：目标评论已被其他管理员处理，返回404。
2. **权限不足**：返回403错误。
3. **未填写操作原因**：前端拦截并提示。

#### UC-O4：负责人接收负面反馈待办

**参与者：** 场地负责人（主要）、管理员（扩展参与者）

**前置条件：**
1. 系统中存在某场地连续多条评分≤2的评论（阈值可配置）。
2. 该场地已指定负责人。
3. 负责人账号已激活。

**基本事件流：**

| 步骤 | 描述 |
|------|------|
| 1 | 系统在评论发表的后置处理中检测到评分≤2。 |
| 2 | 系统异步统计该场地近7天内评分≤2的评论数量。 |
| 3 | 若达到阈值，系统自动为负责人创建待办任务。 |
| 4 | 负责人登录后查看待办详情，进行现场核实。 |
| 5 | 负责人填写处理说明，更新待办状态。 |
| 6 | 若状态更新为"已解决"，系统再次统计验证。 |

**异常事件流：**
1. **场地无指定负责人**：记录日志并通知管理员。
2. **待办积压升级**：超时未处理则通知管理员介入。
3. **低分评论不足阈值**：不创建待办，仅在日志中记录。
4. **并发创建**：通过去重机制避免重复创建待办。

## 四. 实验总结

### 实验中遇到的问题

1. **参与者角色的泛化关系**：保洁运维人员角色可泛化为清洁员、灯光检查员和器材管理员三个子角色，但在用例图中表达这种泛化关系时，容易将"角色泛化"与"用例泛化"混淆。

2. **用例的后置条件描述粒度**：UC-O1的后置条件涉及多个数据库表的更新和可用性状态变更，描述时需要明确每条变更的具体影响范围，粒度太粗会导致歧义，太细则冗长。

3. **异常场景的完整性**：为每个用例编写4-5种异常场景时，容易遗漏系统级异常（如数据库连接失败）和边界条件异常（如并发创建待办的去重）。

### 解决方法

1. **明确泛化层次**：在用例图中将"运维保洁人员"作为抽象参与者，其三个子角色（清洁员、灯光检查员、器材管理员）作为具体参与者，子角色继承父角色的所有用例，并可添加特有用例。这样既保持了用例图的简洁性，又准确表达了角色关系。

2. **分层描述后置条件**：采用"全局后置条件（系统层面）+ 局部后置条件（模块层面）"的分层描述策略。全局描述系统整体状态变化，局部聚焦于具体表字段的变更。在UC-O1中，全局后置条件为"场地可预约性状态更新"，局部后置条件为"t_venue_ops.cleaningStatus更新为PENDING_RECTIFICATION"。

3. **系统化异常分析框架**：采用"输入校验异常→权限校验异常→业务规则异常→系统资源异常"的四层次框架，确保每层至少覆盖一种异常场景。

### 思考与收获

本实验完成了子系统二的面向对象分析与设计。通过识别系统的五类参与者和七个核心用例，构建了完整的用例模型。用例图清晰地展示了参与者与用例的关联关系、用例之间的包含和扩展依赖，以及系统边界的划分。针对四个核心用例（UC-O1至UC-O4），编写了完整的用例规格说明，包括前置条件、后置条件、基本事件流和异常事件流。规格说明中引用了实际的类名、接口路径、方法名和数据库表，确保用例规格与实际系统实现紧密对应。
