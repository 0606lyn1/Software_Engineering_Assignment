## 报告说明

本报告运用结构化分析方法描述子系统二的数据流、ER 模型、状态规则和模块设计，所有内容对照 `stadium` 后端实际实现。`getAvailability()` 为核心可用性评估算法，评论模块当前为直接持久化模型（无审核状态字段）。

## 一. 实验目的

1. 绘制分层 DFD，描述运维与评论数据流。
2. 绘制 ER 图，定义实际数据库实体关系。
3. 绘制状态迁移图，描述运维四维状态变化。
4. 完成总体设计与可用性评估详细设计。

## 二. 实验内容

绘制顶层/0层/1层 DFD、ER 图、状态迁移图，划分模块并给出可用性评估与评论创建伪代码。

## 三. 实验步骤和结果

### 1. 分层数据流图（DFD）

#### 1.1 顶层 DFD

**外部实体：**
- **普通用户（学生/教师）**：查看运维状态、发表评论
- **运维人员（STAFF）/管理员（ADMIN）**：填报运维状态
- **子系统一（预约系统）**：查询场地可约性

**数据流：**
- 运维人员 → 系统：四维状态 + 负责人信息 + 备注
- 普通用户 → 系统：评论内容 { venueId, content }
- 子系统一 → 系统：getAvailability(venueId) 请求
- 系统 → 子系统一：{ available, status, reason }
- 系统 ↔ 数据库：读写 t_venue_ops、t_comment

![](./结构化分析-DFD顶层图.svg)

#### 1.2 0 层 DFD

| 处理 | 职责 | 数据存储 |
| --- | --- | --- |
| P1 运维管理 | 台账查询、状态填报、懒创建 | D1: t_venue_ops |
| P2 评论管理 | 评论发表、列表查询、删除 | D2: t_comment |
| P3 可用性评估 | 四维度阻断判断 | 读 D1, 输出给子系统一 |

**控制流：** P1 状态变更后，P3 在下次查询时自动反映新状态（同步，无消息队列）。

![](./结构化分析-DFD0层图.svg)

#### 1.3 1 层 DFD（P2 评论管理细化）

| 子过程 | 输入 | 处理 | 输出 |
| --- | --- | --- | --- |
| P2.1 接收评论 | POST /api/comments | 提取 venueId, content | Comment 对象 |
| P2.2 身份绑定 | JWT token | findByUsername() → userId | userId |
| P2.3 持久化 | Comment | commentService.save() | INSERT t_comment |
| P2.4 列表查询 | GET /api/comments?venueId= | lambdaQuery 过滤 | 评论列表 |

**注意：** 当前无 P2.x 敏感词过滤、反刷屏检测子过程。

### 3. 状态迁移图

#### 3.1 场地运维四维状态（独立维度，非单一状态机）

各维度独立取值，`getAvailability()` 按优先级顺序检测：

```
检测顺序：maintenance → cleaning → lighting → equipment
首个命中阻断集 → 返回 available=false
全部通过 → 返回 available=true, status="AVAILABLE"
```

**维护维度迁移示例：**
- NORMAL → MAINTENANCE：运维人员填报
- NORMAL → CLOSED：运维人员暂停开放
- MAINTENANCE/CLOSED → NORMAL：维修完成后恢复

**清洁维度迁移示例：**
- CLEAN → NEED_CLEANING：发现待清洁
- NEED_CLEANING → CLEAN：清洁完成
- CLEAN → PENDING_RECHECK：赛后待复检（种子数据 venue_id=2）

#### 3.2 评论生命周期（当前简化模型）

| 状态 | 说明 |
| --- | --- |
| 已发布（隐式） | POST 后直接 save，无 status 字段 |
| 已删除 | DELETE /api/comments/{id} → removeById() 物理删除 |

**未实现：** DRAFT → PENDING_REVIEW → PUBLISHED → HIDDEN 审核流

### 5. 详细设计

#### 5.1 可用性评估算法（对照源码）

```
function getAvailability(venueId):
    ops = getOrCreateByVenueId(venueId)

    if ops.maintenanceStatus in {MAINTENANCE, CLOSED}:
        return { available: false, status: ops.maintenanceStatus,
                 reason: "场馆处于维护或闭馆状态" }

    if ops.cleaningStatus in {NEED_CLEANING, PENDING_RECHECK}:
        return { available: false, status: ops.cleaningStatus,
                 reason: "清洁状态未达开放标准" }

    if ops.lightingStatus == "FAULT":
        return { available: false, status: ops.lightingStatus,
                 reason: "灯光故障待处理" }

    if ops.equipmentStatus in {MISSING, DAMAGED}:
        return { available: false, status: ops.equipmentStatus,
                 reason: "器材缺失或损坏" }

    return { available: true, status: "AVAILABLE",
             reason: "运维状态正常，可进入预约流程" }
```

#### 5.2 运维填报算法

```
function updateOps(venueId, request, operatorName):
    ops = getOrCreateByVenueId(venueId)
    ops.maintenanceStatus = request.maintenanceStatus
    ops.cleaningStatus = request.cleaningStatus
    ops.lightingStatus = request.lightingStatus
    ops.equipmentStatus = request.equipmentStatus
    ops.responsiblePerson = request.responsiblePerson
    ops.contactPhone = request.contactPhone
    ops.remark = request.remark
    ops.lastInspector = operatorName or "unknown"
    ops.lastCheckedAt = now()
    updateById(ops)
    return ops
```

#### 5.3 评论创建流程

```
function createComment(request, authentication):
    user = userService.findByUsername(authentication.getName())
    comment = new Comment()
    comment.userId = user.id
    comment.venueId = request.venueId
    comment.content = request.content
    comment.createdAt = now()
    commentService.save(comment)
    return comment
```

## 四. 实验总结

### 实验中遇到的问题

原 ER 图包含 7 个实体（含 cleaning_log、lighting_log），DFD 包含敏感词过滤子过程，与当前简化实现不符。

### 解决方法

ER 图精简为 db.sql 中实际 5 张表；DFD 评论流程去掉未实现的校验环节；可用性算法直接引用 VenueOpsServiceImpl 源码逻辑。

### 思考与收获

结构化分析清晰揭示了子系统二"运维台账 → 可用性评估 → 预约阻断"的数据流主线，getAvailability() 作为唯一评估入口的设计保证了规则一致性。
