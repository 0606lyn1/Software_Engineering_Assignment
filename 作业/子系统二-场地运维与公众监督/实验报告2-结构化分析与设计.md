# 实验报告2——结构化分析与设计实验

**实验名称：** 实验二 结构化分析与设计实验

**子系统：** 子系统二——场地运维与公众监督子系统

---

## 报告说明

本报告在实验一需求规格说明的基础上，使用结构化分析与设计方法描述子系统二的数据流、数据存储、状态变化和模块设计。子系统二的核心任务是把分散的场地运维信息和公众监督信息转化为可管理、可审计、可联动的系统数据，因此本报告重点说明用户评论、清洁维护记录、灯光设备信息、负责人待办和可用性评估结果在系统中的流转关系。

结构化分析能够帮助明确"场地状态如何被采集、如何被处理、如何影响预约可用性"。通过DFD可以看清普通用户、保洁人员、负责人、管理员和子系统一之间的数据交换；通过ER图可以明确评论、运维记录、设备信息和场地之间的实体关系；通过状态迁移图可以说明运维状态和评论状态如何变化；通过总体设计和详细设计可以把这些分析结果转化为可实现的软件模块。

## 一. 实验目的

本实验旨在运用结构化分析方法对子系统二进行建模与设计。通过绘制分层数据流图（DFD），描述系统内部的数据流动和处理逻辑；通过ER图刻画系统的核心数据实体及其关系；通过状态迁移图描述关键业务对象的状态变化。在此基础上开展总体设计和详细设计，划分系统模块并定义接口和核心算法。通过本实验掌握结构化分析与设计的方法论和实战技能。

## 二. 实验内容

本实验运用结构化分析方法对子系统二进行分层数据流建模、实体关系建模和状态迁移建模。绘制顶层/0层/1层三级DFD图、ER图和状态迁移图，开展系统的总体设计（四层架构、六大模块划分）和详细设计（评论创建流程伪代码、可用性评估算法伪代码），为后续编码实现提供精确指导。

### 实验过程补充说明

本实验按照"外部实体识别—数据流分层—数据存储归纳—实体关系建模—状态迁移分析—模块与算法设计"的顺序进行。首先从实验一的角色场景中提取普通用户、保洁运维人员、场地负责人、管理员和子系统一五类外部交互对象，再梳理他们向系统提交或从系统接收的数据，包括评论内容、评分、清洁记录、维护结果、负责人信息、灯光状态、器材状态和可用性结果。

DFD建模采用自顶向下逐层细化的方法。顶层DFD用于明确场地运维与公众监督系统的整体边界；零层DFD将系统拆分为评论管理、运维管理、负责人管理、设备与器材信息管理、可用性评估等处理过程；一层DFD重点细化评论管理，描述用户提交评论、系统校验预约关联、写入评论记录、触发负面反馈待办、管理员审核违规评论等数据流。这样可以把公众监督从简单留言扩展为完整处理闭环。

ER建模阶段从数据流和数据存储中抽取核心实体，包括场地、用户、评论、预约关联、清洁维护记录、负责人、灯光状态、器材信息、待办事项和可用性评估结果。实体关系设计重点关注三类约束：评论必须能够关联场地和用户，负面评论应能够派生负责人待办，运维和设备状态应能够影响可用性输出。通过ER图可以确保数据库结构能够支撑监督、处理和联动三类业务。

状态迁移建模重点分析场地运维状态和评论生命周期。场地运维状态可能在正常、待清洁、维护中、暂停开放、恢复开放之间切换；评论状态则可能经历待审核、已发布、已隐藏、已处理、已归档等阶段。通过状态迁移图可以提前发现非法流程，例如已隐藏评论不应继续触发普通展示，维护中场地不应输出可预约状态，已归档待办不应再次进入处理中。

总体设计阶段将系统划分为表现层、控制层、业务服务层、数据访问层和外部接口层。详细设计阶段重点补充评论创建流程和可用性评估算法：评论创建需要进行身份校验、预约关联校验、敏感内容检测、评分统计和负面反馈触发；可用性评估需要综合运维状态、灯光状态、器材状态、负责人处理结果和人工锁定标记，最终向子系统一输出可预约、谨慎预约或不可预约的判断结果。

## 三. 实验步骤和结果

### 1. 分层数据流图（DFD）

#### 1.1 顶层DFD（场地运维与公众监督系统）

顶层DFD将整个子系统二视为一个黑盒处理过程，展示系统与四个外部实体之间的数据流交互：

- **普通用户（学生/教师）**：向系统发送"查看运维状态"请求和"发表评论/评分"，系统返回"状态/评论数据显示"。
- **保洁运维人员**：向系统发送"清洁打卡/灯光记录/器材更新"数据流，系统返回"保存确认"。
- **管理员**：向系统发送"处理评论/配置负责人"数据流，系统返回"操作结果"。
- **子系统一（场地预约系统）**：向系统发送"查询可用性请求"，系统返回"场地可用性数据"。

#### 1.2 零层DFD

零层DFD将子系统二分解为三个核心处理过程：

**P1: 运维管理**——负责清洁打卡处理、灯光状态更新、器材信息管理和负责人配置。读写 `D1: t_venue_ops` 数据存储。当运维状态变更时向 P3 发送"触发可用性重算"控制流。

**P2: 评论管理**——负责评论发表与展示、敏感词过滤、反刷屏控制和违规评论处理。读写 `D2: t_comment` 数据存储。

**P3: 可用性输出**——负责可用性评估、状态码生成、原因文本输出和维护标志列表生成。读取 `D1: t_venue_ops` 和 `D3: t_venue` 数据存储，向子系统一输出场地可用性数据。

**0层DFD图示：**

![](./结构化分析-DFD0层图.svg)

#### 1.3 一层DFD：评论管理的细化

评论管理（P2）的细化处理流程如下：

1. **评论提交处理（P2.1）**：接收来自前端的 `POST /api/comments` 请求，提取用户ID、场地ID、评分和内容。
2. **校验过滤处理（P2.2）**：依次执行反刷屏检测（`checkSpam()`，检查用户-场地60秒冷却）和敏感词过滤（`filterSensitiveWords()`，匹配配置词库）。
3. **存储处理（P2.3）**：将通过校验的评论数据写入 `INSERT INTO t_comment`。
4. **展示处理（P2.4）**：按条件查询 `t_comment` 表，关联用户表获取用户名，按时间倒序返回。

### 3. 状态迁移图

#### 3.1 场地运维状态迁移

场地运维信息的核心状态为 `maintenanceStatus` 枚举，其状态迁移规则如下：

- **NORMAL → MAINTENANCE**：管理员设置 maintenanceStatus=MAINTENANCE
- **MAINTENANCE → NORMAL**：维修完成后管理员恢复
- **NORMAL → PENDING_RECTIFICATION**：保洁打卡 cleaningStatus=PENDING_RECTIFICATION
- **PENDING_RECTIFICATION → NORMAL**：重新清洁并检查通过后恢复
- **NORMAL → FULL_FAULT_LIGHTING**：lightingStatus=FULL_FAULT，禁止夜间户外预约
- **FULL_FAULT_LIGHTING → NORMAL**：灯具全部修复后恢复正常

#### 3.2 评论生命周期状态迁移

评论状态包括：**DRAFT（草稿）→ PENDING_REVIEW（待审核）→ PUBLISHED（已发布）→ HIDDEN（已隐藏）→ DELETED（已删除）**。

- 用户提交评论后，若无敏感词则直接进入 PUBLISHED 状态
- 管理员可将 PUBLISHED 评论设为 HIDDEN 或 DELETED
- 作者可自删评论
- 删除操作需记录审计日志

### 4. 总体设计

#### 4.1 技术架构分层

系统采用经典的四层架构：

- **表示层**：`VenueOpsController`、`CommentController`，接收HTTP请求，返回JSON响应。
- **业务层**：`VenueOpsServiceImpl`、`CommentServiceImpl`，执行核心业务逻辑。
- **持久层**：`VenueOpsMapper`、`CommentMapper`，基于 MyBatis-Plus `BaseMapper<T>`。
- **数据层**：`VenueOps`、`Comment`，ORM实体映射到数据库表。

#### 4.2 模块划分

| 模块编号 | 模块名称 | 核心功能 | 关键类 |
|---------|---------|---------|-------|
| M1 | 清洁台账模块 | 清洁打卡、记录查询、可预约性联动 | VenueOpsController, VenueOpsServiceImpl |
| M2 | 负责人管理模块 | 负责人CRUD、变更历史、电话脱敏 | VenueOpsServiceImpl.maskPhone() |

### 5. 详细设计

#### 5.1 评论创建流程伪代码

```
FUNCTION createComment(CommentCreateRequest req, Long userId):
    // 步骤1: 反刷屏检测
    lastComment = t_comment SELECT MAX(created_at)
                  WHERE user_id = userId AND venue_id = req.venueId
    IF lastComment IS NOT NULL AND (NOW() - lastComment) < 60s THEN
        THROW AntiSpamException("请稍候60秒后再发表评论")
    END IF

    // 步骤2: 敏感词过滤
    sensitiveWords = CONFIG "comment.sensitive-words" SPLIT BY ","
    FOR EACH word IN sensitiveWords:
        IF req.content CONTAINS word THEN
            THROW SensitiveWordException("评论包含敏感词: " + word)
        END IF
    END FOR

    // 步骤3: 重复内容检测
    duplicate = SELECT COUNT(*) FROM t_comment
                WHERE user_id = userId AND venue_id = req.venueId
                AND content = req.content
    IF duplicate > 0 THEN
        THROW DuplicateContentException("请勿重复发表相同内容")
    END IF

    // 步骤4: 保存评论
    comment = NEW Comment()
    comment.userId = userId
    comment.venueId = req.venueId
    comment.rating = req.rating
    comment.content = req.content
    comment.createdAt = NOW()
    t_comment INSERT comment

    // 步骤5: 检查是否需要生成负责人待办
    IF req.rating <= 2 THEN
        recentNegativeCount = SELECT COUNT(*) FROM t_comment
                              WHERE venue_id = req.venueId
                              AND rating <= 2
                              AND created_at > (NOW() - 7 DAYS)
        IF recentNegativeCount >= THRESHOLD THEN
            CREATE_TODO(venueId, "负面反馈待办")
        END IF
    END IF

    RETURN comment
END FUNCTION
```

#### 5.2 可用性评估算法伪代码

```
FUNCTION evaluateAvailability(Long venueId):
    ops = t_venue_ops SELECT WHERE venue_id = venueId
    venue = t_venue SELECT WHERE id = venueId

    response = NEW VenueAvailabilityResponse()
    response.maintenanceFlags = NEW ArrayList()

    // 规则1: 维护状态检查
    IF ops.maintenanceStatus == MAINTENANCE THEN
        response.reservable = FALSE
        response.reasonCode = "MAINTENANCE"
        response.displayMessage = "场地维护中，暂不可预约"
        RETURN response
    END IF

    // 规则2: 清洁状态检查
    IF ops.cleaningStatus == PENDING_RECTIFICATION
       AND schoolConfig.blockOnCleaningFail THEN
        response.reservable = FALSE
        response.reasonCode = "CLEANING_FAIL"
        response.displayMessage = "场地清洁未达标，暂不可预约"
        RETURN response
    END IF

    // 规则3: 灯光检查（仅影响夜间户外场地）
    IF ops.lightingStatus == FULL_FAULT
       AND venue.isOutdoor
       AND CURRENT_TIME.isNighttime() THEN
        response.reservable = FALSE
        response.reasonCode = "LIGHTING_FAULT"
        response.displayMessage = "场地灯光故障，夜间不可预约"
        RETURN response
    END IF

    // 通过所有检查
    response.reservable = TRUE
    response.reasonCode = "OK"
    response.displayMessage = "场地可预约"
    RETURN response
END FUNCTION
```

## 四. 实验总结

### 实验中遇到的问题

1. **DFD分层粒度的统一性**：子系统二的流程比子系统一简单，在绘制DFD时，0层图分解为三个处理过程（运维管理、评论管理、可用性输出），但1层图如果只细化评论管理而不细化运维管理，会导致各分支细化深度不一致。

2. **状态迁移图的并发状态问题**：场地运维状态由多个枚举字段共同决定（maintenanceStatus、cleaningStatus、lightingStatus），单一字段的状态机无法完整描述场地的综合状态，多字段组合会导致状态数量呈指数增长。

3. **伪代码与API接口的实际对应**：详细设计中的伪代码直接引用了数据库表名和字段名，但在后续开发中可能会调整数据库设计，导致伪代码与实际实现不一致。

### 解决方法

1. **按业务复杂度选择性细化**：评论管理是子系统二中交互逻辑最复杂的模块（涉及反刷屏、敏感词过滤、待办生成等多重操作），因此选择将其细化到1层。运维管理模块的操作相对标准化，保持在0层粒度。

2. **采用层次化状态机**：设计主状态（maintenanceStatus）和子状态（cleaningStatus、lightingStatus）分离的层次化状态机结构。主状态决定场地是否可预约，子状态在特定条件下影响主状态的评估结果，通过evaluateAvailability()统一汇总为最终的可用性输出。

3. **建立代码-文档同步机制**：在伪代码中使用逻辑描述而非具体表名，将数据库表名和字段名作为配置信息管理。当数据库设计变更时，只需更新配置映射而不必修改伪代码逻辑。

### 思考与收获

本实验完成了子系统二的结构化分析与设计。在数据流分析方面，绘制了顶层DFD、0层DFD和1层DFD，逐层细化了系统的数据处理逻辑。在数据建模方面，通过ER图刻画了7个核心实体及其关系。在状态建模方面，分别为场地运维状态和评论生命周期绘制了状态迁移图。在总体设计方面，将系统划分为6个功能模块，采用经典的四层架构。在详细设计方面，给出了评论创建流程和可用性评估算法的完整伪代码。结构化分析方法为理解系统的功能和数据逻辑提供了直观而严谨的视图。
