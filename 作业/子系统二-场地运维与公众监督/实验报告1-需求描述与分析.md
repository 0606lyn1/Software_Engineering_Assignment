# 实验报告1——需求描述与分析实验

**实验名称：** 实验一 需求描述与分析实验

**子系统：** 子系统二——场地运维与公众监督子系统

**技术栈：** Java 17 + Spring Boot 3.4.4 + MyBatis-Plus + Spring Security JWT + MySQL 8.4 / Vue 3 + Vite + Ant Design Vue + TypeScript

**对应代码：** `VenueOpsController`、`VenueOpsServiceImpl`、`CommentController`、`VenueMaintenance.vue`、`VenueList.vue`、`CommentList.vue`

---

## 报告说明

本报告基于当前已实现的场地运维与公众监督功能进行需求分析。子系统二通过 `t_venue_ops` 表维护场地四维运维状态（维护/清洁/灯光/器材），通过 `getAvailability()` 向子系统一输出可约性判断；通过 `t_comment` 表支持公众文字评论。清洁打卡在当前实现中等价于运维人员通过 `PUT /api/venue-ops/{venueId}` 更新 `cleaningStatus` 并记录 `lastInspector`、`lastCheckedAt`。

## 一. 实验目的

1. 梳理场地运维与公众监督的用户角色与业务场景。
2. 开展技术、经济、操作三维度可行性分析。
3. 定义功能与非功能需求，与源码实现保持一致。
4. 明确与子系统一的可用性联动接口契约。

## 二. 实验内容

确定实验主题，梳理四类用户角色场景，定义 FR-O1 至 FR-O5 功能需求模块，撰写需求规格说明书摘要。

### 2. 可行性分析

#### 2.1 技术可行性

运维台账采用 `t_venue_ops` 一对一关联 `t_venue`，`VenueOpsServiceImpl` 已实现懒创建（`getOrCreateByVenueId`）和四维度阻断规则。评论模块基于 MyBatis-Plus 标准 CRUD，技术成熟可行。

#### 2.2 经济可行性

与子系统一共用单体应用和数据库，无额外基础设施成本，经济可行。

#### 2.3 操作可行性

`VenueMaintenance.vue` 提供四维状态下拉选择和 PASS/HOLD 可用性预览，颜色编码（红/橙/绿）直观展示风险等级，运维人员学习成本低。

### 4. 非功能需求定义

| 类别 | 描述 | 当前实现 |
| --- | --- | --- |
| 数据完整性 | 一馆一条运维记录 | t_venue_ops.venue_id UNIQUE |
| 权限控制 | 运维填报需 ADMIN/STAFF | @PreAuthorize on PUT |
| 公开查询 | GET 运维/评论/可约性匿名可访问 | SecurityConfig 放行 |
| 接口稳定性 | 可约性判断逻辑集中在一处 | getAvailability() 单入口 |
| 实时性 | 填报后立即影响预约 | 同步服务内调用，无消息队列 |

## 四. 实验总结

### 实验中遇到的问题

原需求描述引用了 `t_cleaning_log`、`maskPhone()`、`CommentServiceImpl.validateBeforeCreate()` 等未实现组件，与源码不符。

### 解决方法

以 `VenueOpsServiceImpl.java`、`CommentController.java`、`db.sql` 为准重新定义需求，区分已实现与规划项。

### 思考与收获

子系统二的核心价值是"运维状态 → 可约性判断 → 预约阻断"的闭环。即使评论模块当前为简化版，运维台账与可用性评估已构成与子系统一的关键集成点。
