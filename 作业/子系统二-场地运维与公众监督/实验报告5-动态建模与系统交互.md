# 实验报告5——动态建模与系统交互实践

**实验名称：** 实验五 动态建模与系统交互实践

**子系统：** 子系统二——场地运维与公众监督子系统

---

## 一、实验目的

本实验旨在运用UML动态建模技术对子系统二的核心业务流程和对象交互进行建模。通过顺序图（Sequence Diagram）和通讯图（Communication Diagram）刻画对象之间的消息传递和时间顺序；通过状态图（State Machine Diagram）描述关键对象的生命周期和状态变迁；通过活动图（Activity Diagram）展示业务流程的分支、并行和对象流动。通过本实验掌握面向对象动态建模的方法论，为系统实现提供精确的行为规范。

## 二、顺序图

### 2.1 场景一：用户发表评论完整流程

本顺序图展示了从用户打开场地详情到新评论显示的完整交互过程，跨越六个对象生命线：用户（User）、VenueList.vue、CommentList.vue、CommentController、CommentService、MySQL。

**消息流如下：**

1. 用户在 `VenueList.vue` 页面中点击某场地，打开场地详情。
2. 用户点击"查看评论"按钮，`VenueList.vue` 打开抽屉并加载 `CommentList.vue` 组件。
3. `CommentList.vue` 组件挂载时调用 `GET /api/comments?venueId={id}` 获取已有评论列表。
4. `CommentController.list()` 接收请求，调用 `CommentService.listLatest(venueId, keyword)`。
5. Service 执行 SQL `SELECT * FROM t_comment WHERE venue_id = ? ORDER BY created_at DESC`（关联用户表获取username）。
6. 数据库返回评论列表（含用户名），逐层返回给 `CommentList.vue`，渲染为评论列表。

**发表评论的 alt 分支：**

7. 用户在评论表单中输入评分（1-5星）和评论内容（≤500字），点击提交。
8. `CommentList.vue` 发送 `POST /api/comments` 请求，携带 `CommentCreateRequest` JSON body。
9. `CommentController.create()` 接收请求并调用 `CommentService.validateBeforeCreate(userId, venueId, content)`。
10. Service 自调用 `checkSpam(userId, venueId)`：查询该用户对该场地在60秒内是否有评论记录。若检测到刷屏，返回429错误。
11. Service 自调用 `filterSensitiveWords(content)`：遍历 `application.yml` 中配置的敏感词列表（诈骗、赌博、代打、代练、广告等）。若命中，返回400错误。
12. 两重校验通过后，Service 构造 `Comment` 实体并调用 Mapper 执行 `INSERT INTO t_comment (user_id, venue_id, rating, content, created_at) VALUES (...)`。
13. 数据库返回保存成功确认。
14. Service 返回 `Comment` 对象给 Controller，Controller 返回 201 Created + Comment JSON。
15. `CommentList.vue` 收到成功响应后，重新调用 `GET /api/comments` 刷新评论列表。
16. 用户看到新评论出现在列表顶部。

### 2.2 场景二：管理员更新场地运维信息并触发可用性变化

本顺序图展示了管理员通过 `AdminManage.vue` 修改场地运维配置并触发可用性重算的完整流程，跨越六个对象生命线：管理员、AdminManage.vue、VenueOpsController、VenueOpsService、MySQL、子系统一。

**消息流如下：**

1. 管理员登录系统，进入 `AdminManage.vue` 后台页面。
2. 在场地管理 Tab 中，管理员点击某场地的"运维"按钮。
3. `AdminManage.vue` 发送 `GET /api/venue-ops/{venueId}` 加载当前运维配置。
4. `VenueOpsController.getOps()` 调用 `VenueOpsService.getOrCreateByVenueId(venueId)`（若运维记录不存在则自动创建默认记录）。
5. Service 查询 `SELECT * FROM t_venue_ops WHERE venue_id = ?`。
6. 返回 `VenueOps` 实体（电话经 `maskPhone()` 脱敏），前端展示运维配置弹窗。

**更新运维信息的 alt 分支：**

7. 管理员在弹窗中修改字段，例如将 `maintenanceStatus` 设为 MAINTENANCE，将 `cleaningStatus` 设为 PENDING_RECTIFICATION。
8. 管理员点击保存，前端发送 `PUT /api/venue-ops/{venueId}` 请求，携带 `VenueOpsUpdateRequest` JSON body（仅含被修改的字段）。
9. `VenueOpsController.updateOps()` 接收请求（需验证管理员权限），调用 `VenueOpsService.updateByVenueId(updateReq)`。
10. Service 执行 `UPDATE t_venue_ops SET maintenance_status = ?, cleaning_status = ?, updated_at = NOW() WHERE venue_id = ?`。
11. 更新完成后，Service 自调用 `evaluateAvailability(venueId)` 评估新的可预约性：
    - 检查 `maintenanceStatus == MAINTENANCE` → 返回 `reservable=false, reasonCode="MAINTENANCE"`
    - 检查 `cleaningStatus == PENDING_RECTIFICATION` → 可能进一步影响可预约性
    - 检查灯光状态和夜间时段判断
12. Service 生成 `VenueAvailabilityResponse`：`{reservable: false, reasonCode: "MAINTENANCE", displayMessage: "场地维护中，暂不可预约", maintenanceFlags: ["维护中"]}`。
13. 返回更新结果和可用性报告给 Controller。
14. Controller 返回 200 OK + `VenueAvailabilityResponse` JSON 给前端。
15. 前端弹窗显示更新成功确认及场地不可预约状态提示。
16. 系统异步通知子系统一：可用性状态已变更（采用最终一致性，子系统一在下次调阅 `GET /api/venue-ops/{venueId}/availability` 时感知变更）。

## 三、通讯图

基于场景一（用户发表评论）的顺序图转换为通讯图，展示六个对象（用户、VenueList/CommentList、CommentController、CommentServiceImpl、t_comment数据库、敏感词过滤器、反刷屏检测）之间的链接和消息传递。

**消息序列（编号与顺序图对应）：**

1. ① 用户 → VenueList：打开场地详情，输入评论
2. ② CommentList → CommentController：`POST /api/comments`
3. ③ CommentController → CommentServiceImpl：`validateBeforeCreate(userId, venueId, content)`
4. ④ CommentServiceImpl → 敏感词过滤器：`filterSensitiveWords(content)`，匹配配置词库
5. ⑤ CommentServiceImpl → 反刷屏检测：`checkSpam(userId, venueId)`，检查60秒冷却
6. ⑥ CommentServiceImpl → t_comment (MySQL)：`INSERT INTO t_comment`，将校验通过的评论持久化
7. ⑦ t_comment → CommentServiceImpl：返回保存成功信号
8. ⑧ CommentServiceImpl → CommentController：返回 `Comment` 对象
9. ⑨ CommentController → CommentList：返回 `201 Created + Comment JSON`
10. ⑩ CommentList → 用户：刷新评论列表，显示新评论

通讯图关注对象间的结构链接和消息传递方向，与顺序图为UML中语义等价的两种不同交互视图。顺序图侧重时间顺序，通讯图侧重对象间的链路关系。

## 四、状态图

### 4.1 场地运维状态图

场地运维信息（`VenueOps`）的状态机以 `maintenanceStatus` 和 `lightingStatus` 两个核心枚举字段的取值作为状态，以管理员操作和系统事件作为状态迁移触发条件。

**核心状态：**
- **NORMAL**（正常使用）：场地可预约，可评论，为系统初始状态。
- **MAINTENANCE**（维护中）：管理员通过 `PUT /api/venue-ops/{id}` 设置，禁止预约。
- **PENDING_RECTIFICATION**（待整改）：保洁打卡结果为"不合格"触发，视配置禁止预约。
- **FULL_FAULT_LIGHTING**（灯光全故障）：`lightingStatus=FULL_FAULT` 且场地为户外，禁止夜间预约。

**迁移规则：**
- NORMAL → MAINTENANCE：管理员设置维护 / 报修触发
- MAINTENANCE → NORMAL：维修完成·管理员恢复
- NORMAL → PENDING_RECTIFICATION：保洁打卡 cleaingStatus=PENDING_RECTIFICATION
- PENDING_RECTIFICATION → NORMAL：重新清洁·检查通过
- NORMAL → FULL_FAULT_LIGHTING：灯区全部故障
- FULL_FAULT_LIGHTING → NORMAL：灯具全部修复

**灯光复合状态：** 灯光系统作为场馆运维的子状态机，包含三个子状态：LIGHTING_NORMAL（灯光正常）→ PARTIAL_FAULT（部分灯具故障）→ FULL_FAULT（全部故障）。三种灯光状态均可恢复至正常状态。

无论主状态或灯光子状态发生变更，均触发出口动作 `evaluateAvailability()`，汇总生成 `VenueAvailabilityResponse` 推送给子系统一。

## 五、活动图

活动图以游泳道（Swimlane）形式展示"用户发表评论"的完整业务流程，划分为四个泳道：用户、前端（Vue3）、后端（Spring Boot）、数据库（MySQL）。

**业务流程如下：**

1. **开始** → 用户打开场地详情页（VenueList → 点击场地）。

2. **用户泳道**：用户点击"写评论"按钮，触发前端组件交互。

3. **前端泳道**：CommentList.vue 显示评论表单（Rating 星级评分 + Textarea 文字输入，max 500字）。用户填写评分和内容后点击提交。前端执行客户端校验（字数/评分有效性）。

4. **决策节点一（校验通过？）**：
   - [否]：返回用户泳道，提示修改（字数超限 / 评分无效），用户重新填写
   - [是]：HTTP POST /api/comments，转入后端泳道

5. **后端泳道**——并行执行两条校验路径：
   - 路径A：`checkSpam(userId, venueId)` 反刷屏检测（60秒冷却）
   - 路径B：`filterSensitiveWords(content)` 敏感词过滤（匹配配置词库）

6. **决策节点二（刷屏？）**：
   - [是]：返回前端泳道，显示"请稍候60秒后再发表评论"
   - [否]：继续

7. **决策节点三（敏感词？）**：
   - [是]：返回前端泳道，显示"评论包含敏感词，请修改后重新提交"
   - [否]：继续到数据库泳道

8. **数据库泳道**：执行 `INSERT INTO t_comment (user_id, venue_id, rating, content, created_at) VALUES (...)`。

9. 数据库返回保存成功 → 后端生成 `201 Created + Comment JSON` → 前端 `CommentList.vue` 重新调用 `GET /api/comments` 刷新列表 → 用户在评论列表中看到新评论。

10. **异步分支（评分≤2时）**：触发 UC-O4 负责人待办生成流程（与主流程并行，不阻塞评论显示）。

11. **结束**。

活动图清晰地展示了用户评论从提交到展示的全过程，包含三个决策分支和两条并行校验路径，以及前后端之间的职责划分。

## 六、实验总结

本实验完成了子系统二的动态建模与系统交互实践。在顺序图方面，选取了两个核心场景进行建模：用户发表评论的完整流程（跨越6个对象、18条消息）和管理员更新场地运维的流程（跨越6个对象、17条消息，含可用性评估自调用），精确刻画了对象间消息传递的时间顺序和嵌套调用关系。在通讯图方面，将用户评论场景的顺序图等价转换为通讯图，突出了对象之间的链接结构。在状态图方面，为场地运维状态设计了包含主状态和灯光复合子状态的两层状态机，明确了各状态的进入、退出条件和迁移触发事件。在活动图方面，以四泳道形式展示了用户发表评论的完整业务流程，包含三个决策节点、两条并行校验路径和异步触发分支，实现了跨角色职责的精确分工。四种动态视图相互补充，从时间序列、对象通信、状态变迁和流程控制四个维度完整刻画了子系统二的行为模型，为后续的编码实现和测试用例设计提供了精确的规范指导。
