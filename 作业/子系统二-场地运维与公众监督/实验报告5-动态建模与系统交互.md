# 实验报告5——动态建模与系统交互实践

**实验名称：** 实验五 动态建模与系统交互实践

**子系统：** 子系统二——场地运维与公众监督子系统

**对应代码：** `VenueMaintenance.vue`、`CommentList.vue`、`VenueOpsServiceImpl.java`、`CommentController.java`

---

## 报告说明

本报告描述子系统二两个核心场景的运行时交互：运维人员填报场地状态、用户发表评论。所有消息序列对照实际源码，修正原报告中不存在的 CommentServiceImpl 校验链和异步通知子系统一等流程。

## 一. 实验目的

1. 绘制顺序图，描述运维填报和评论发表交互。
2. 绘制通讯图，展示对象协作拓扑。
3. 绘制状态图，描述运维四维状态与可约性关系。
4. 绘制活动图，描述运维填报业务流程。

## 二. 实验内容

针对"运维人员填报场地状态"和"用户发表评论"两个场景进行动态建模，补充运维状态与可约性状态图。

| 序号 | 调用方 | 被调方 | 消息 | 说明 |

### 3. 状态图

#### 3.1 场地可约性判断（由四维状态组合驱动）

```
[getAvailability 入口]
    │
    ├─ maintenance ∈ {MAINTENANCE, CLOSED} → 不可约
    ├─ cleaning ∈ {NEED_CLEANING, PENDING_RECHECK} → 不可约
    ├─ lighting = FAULT → 不可约
    ├─ equipment ∈ {MISSING, DAMAGED} → 不可约
    └─ 全部通过 → AVAILABLE（可约）
```

**各维度独立迁移，无全局单一状态。** 例如 venue_id=2 仅 cleaningStatus=PENDING_RECHECK 即阻断，其余维度正常。

#### 3.2 评论生命周期（简化）

```
[用户发表评论] → 已发布（无 status 字段） → [DELETE] → 物理删除
```

### 4. 活动图

**场景：** 运维人员填报场地状态（四泳道）

## 四. 实验总结

### 实验中遇到的问题

原报告描述了 18 步评论流程（含敏感词过滤器、反刷屏检测、异步通知子系统一），与实际 9 步直接持久化流程差距较大。

### 解决方法

按 CommentController.create() 的实际 55 行代码重写顺序图和活动图，删除未实现的中间对象。

### 思考与收获

动态建模清晰展示了子系统二的两条主线：运维填报影响 getAvailability()，评论发表独立运行但与场馆 Public Supervision 目标一致。与子系统一的同步联动（预约阻断）是跨子系统动态建模的关键验证点。
